# Issue 61883

## Incorrect Reachability Caching Leading to Unpropagated Memory Values

**Description**:
The bug is triggered in optimization passes that rely on optimistic fixpoint iteration to determine block liveness and instruction reachability. The problematic LLVM IR pattern involves memory operations—such as stores and loads to a local variable or allocation—scattered across multiple basic blocks with complex control flow.

During the analysis phase, the compiler evaluates whether a specific definition (e.g., a store) can reach a particular use (e.g., a load). Initially, the compiler may optimistically assume that certain intermediate control-flow paths are dead, leading to the conclusion that the definition cannot reach the use.

However, a flaw in the analysis logic causes it to fail to properly cache this "unreachable" result and register the corresponding dependencies for future updates. As the analysis progresses and the intermediate blocks are later proven to be live (reachable), the initial reachability result is not re-evaluated because the dependency tracking was missed.

Consequently, the compiler operates on the stale assumption that the definition cannot reach the use. This incorrect reachability information causes the transformation logic to aggressively and erroneously optimize the IR. It removes the stores or the entire allocation without propagating the stored values to the loads, leading to a miscompilation where valid program values are silently discarded.

# Issue 64613

## Incorrect Capture Tracking for Pointers Stored to Memory

### Description

The bug is triggered by a sequence of operations where a pointer's escape paths are not fully tracked after it is written to memory. The strategy to trigger this miscompilation involves the following steps:

1. **Pointer Argument Passing**: A pointer to a local allocation (e.g., an `alloca`) is passed as an argument to a function.
2. **Store to Memory**: Inside the called function, the pointer argument is stored into memory (such as another local allocation).
3. **Reload and Escape**: The pointer is subsequently reloaded from that memory and escapes the function, typically by being returned to the caller or cast to an integer.
4. **Flawed Attribute Deduction**: The interprocedural attribute deduction pass analyzes the store instruction but gives up on tracking the subsequent reloads. However, it incorrectly records the pointer as only being "captured in memory," failing to conservatively assume that the reloaded pointer could also be returned or cast to an integer.
5. **Incorrect Attributes**: Because the analysis misses the return/integer capture paths, it incorrectly infers attributes for the pointer argument (e.g., deducing that the pointer is not returned or marking it with `nocapture`).
6. **Invalid Memory Optimization**: A subsequent memory optimization pass (such as Dead Store Elimination) relies on these flawed attributes. Believing that the original pointer does not escape or is not returned by the call, the optimizer assumes that any subsequent accesses using the returned pointer do not alias with the original allocation. Consequently, it incorrectly eliminates valid stores to the original memory in the caller function, resulting in a miscompilation.

# Issue 64959

## Inter-Procedural Reachability Analysis Crash via Nested Queries and Dangling Pointers

**Description**:
The bug is triggered by a complex call graph with multiple functions and cross-function invocations, typically generated by outlining mechanisms (such as OpenMP parallel or target regions). This structure forces the compiler to perform extensive inter-procedural reachability analysis to determine if certain instructions can reach others across function boundaries.

During the optimization pipeline, the compiler's analysis framework evaluates these reachability queries. If a source instruction is not the entry point of its containing function, the analysis recursively triggers a nested query to check if the function's entry block can reach the target instruction.

When this nested reachability query is evaluated during the iterative update phase of the analysis, the compiler creates a temporary, stack-allocated object to hold the query information. However, due to flawed state tracking during the update phase, the compiler incorrectly treats this temporary object as a permanent query and retains a pointer to it in its internal reachability cache.

Once the nested query completes, the stack-allocated object goes out of scope and is destroyed, leaving a dangling pointer in the cache. As the analysis continues, subsequent nested queries allocate new temporary objects at the exact same stack memory address. When the compiler attempts to insert these new queries into the cache, it creates duplicate keys in the underlying hash map. This memory reuse and collision corrupt the data structure, ultimately triggering an assertion failure and crashing the compiler when the hash map attempts to resize or rehash.

# Issue 81793

## Constant Folding of Loads from Memory with Padded Types

**Description**:
The bug is triggered when the compiler attempts to constant-fold a load instruction that reads from a memory location initialized or stored with a uniform constant (e.g., all ones) of a type that requires padding in memory. This occurs when a type's bit size is not equal to its store size (for example, an `i9` type which occupies 16 bits in memory).

In such cases, the padding bits are technically undefined or zero-extended by the backend. However, the optimization logic incorrectly assumes that the entire memory representation, including the padding bits, shares the same uniform pattern as the valid bits of the constant. Consequently, when a value is loaded from this memory location—especially on big-endian targets where the load might directly read the padding bits—the compiler erroneously folds the load into a uniform constant.

The strategy to trigger this miscompilation involves storing a uniform constant of a non-byte-aligned (padded) type and subsequently loading a value from that same memory location, causing the compiler to incorrectly evaluate the load based on the uninitialized or zeroed padding bits.
