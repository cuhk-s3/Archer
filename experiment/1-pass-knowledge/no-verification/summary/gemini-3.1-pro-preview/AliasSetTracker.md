# Subsystem Knowledge for AliasSetTracker
## Elements Frequently Missed

* **Maximum Access Size in MustAlias Sets**: The `AliasSetTracker` frequently misses updating the access size of the representative pointer when a subsequent memory operation accesses the same pointer with a larger size. It only records the initial access size.
* **Representative Pointer Bounds Synchronization**: The spatial bounds (memory footprint) associated with the representative pointer of an alias set are missed during updates, failing to reflect the union or maximum of all access sizes to that specific pointer.
* **Partial Memory Overlaps**: Memory overlaps that occur strictly outside the initial, smaller access size but within a subsequent, larger access size are missed during alias queries because the tracker evaluates the query against the stale size of the representative pointer.

## Patterns Not Well Handled

### Pattern 1: Varying Access Sizes to the Same Pointer
This pattern involves a sequence of memory operations that access the exact same pointer (or strictly must-aliasing pointers) but with increasing access sizes (e.g., an `i8` load followed by an `i64` load, or a scalar store followed by a vector store). The `AliasSetTracker` is not well-equipped to handle this because it establishes the `MustAlias` set's representative pointer using the size of the very first access. When the larger access occurs, the tracker updates the specific entry but fails to propagate this larger size to the representative pointer, leaving the alias set with an artificially truncated memory footprint.

### Pattern 2: Adjacent Memory Accesses Overlapping with Unupdated Bounds
This pattern occurs when a memory operation accesses a region that is adjacent to the initial small access but falls entirely within the bounds of the subsequent larger access. The `AliasSetTracker` handles this poorly because alias queries are checked against the representative pointer. Since the representative pointer retains the stale, smaller size from the initial access, the tracker incorrectly concludes `NoAlias` for the adjacent access, completely ignoring the fact that the larger access encompasses this memory region.

### Pattern 3: Code Motion Based on Stale MustAlias Sets
This pattern involves optimization passes, such as Loop Invariant Code Motion (LICM), querying the `AliasSetTracker` to determine if memory operations can be safely hoisted or sunk. It is not well handled because the optimization pass blindly trusts the flawed `NoAlias` results generated by the unupdated representative pointer sizes. Consequently, the pass incorrectly assumes there are no memory dependencies and performs illegal transformations, such as hoisting a load or store past an aliasing memory operation, which ultimately leads to miscompilations.
