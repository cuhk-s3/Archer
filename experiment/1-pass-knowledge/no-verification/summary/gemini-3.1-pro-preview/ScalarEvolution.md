# Subsystem Knowledge for ScalarEvolution
## Elements Frequently Missed

*   **Deep Poison Dependencies in Instruction Trees**: The optimization pass frequently misses that poison can originate from operands or deeper instructions in a computation graph, rather than just the root instruction's flags (e.g., `nsw`/`nuw`). It also misses poison from operations that mathematically fold away in SCEV (like `0 * %poison`).
*   **Context-Dependence of No-Wrap Flags**: The pass misses that poison-generating flags (`nsw`, `nuw`, `exact`) are context-specific. When instructions are hoisted, reused, or globally cached, the original local guarantees that justified these flags are frequently no longer valid.
*   **Sign-Extension vs. Zero-Extension on Wide Integers**: When dealing with integers wider than 64 bits (e.g., `i128`), the pass frequently misses the need to sign-extend negative multiplicity factors (like `-1`), incorrectly zero-extending them and producing massive positive values.
*   **Arithmetic vs. Logical Shifts for Negative Constants**: During SCEV factorization, the pass misses the distinction between arithmetic and logical right shifts when factoring out powers of two from negative constants, inadvertently transforming small negative multipliers into large positive ones.
*   **Truncation Effects on Sign Bits and Overflow**: The pass frequently misses that truncating an integer can alter its sign bit (invalidating properties like the `samesign` flag) and that truncated loop exit counts can hide wrap-around effects even if the induction variable's start is zero and step is positive.
*   **Iteration-Specific Value Dominance**: The pass misses the distinction between *definition* dominance and *value* dominance. It incorrectly assumes that because an induction variable's definition dominates a merge point, its specific value is safe to use for implication across different loop iterations.
*   **Internal SCEV Cache References During Invalidation**: When invalidating caches due to CFG changes (like LCSSA phi nodes becoming non-trivial), the pass relies solely on explicit IR use-def chains and misses internal SCEV references (such as Backedge Taken Counts) that cached the loop-defined expressions.
*   **Scope-Specific Constant Folding of Unanalyzable Instructions**: The pass misses that typically "unanalyzable" instructions (like memory loads) can be constant-folded at specific scopes if their loop-dependent operands resolve to constants. This causes the cache invalidation logic to truncate prematurely.
*   **Original Guard Conditions for Faulting Operations**: When expanding sequential expressions back into IR, the pass frequently misses the preservation of original short-circuiting semantics or conditional guards, leading to the unconditional execution of faulting operations (like division by zero).
*   **Start Value Checks in Zero-Stride Loops**: The pass misses checking whether the start value of a recurrence already satisfies the loop exit condition before assuming that a zero-stride loop will iterate infinitely and invoke undefined behavior.

## Patterns Not Well Handled

### Pattern 1: Instruction Reuse and Expansion with Mismatched Poison Semantics
During SCEV expansion, the compiler attempts to minimize redundant computations by reusing existing IR instructions that mathematically evaluate to the same SCEV expression. This pattern is poorly handled because SCEV abstracts away poison semantics (e.g., simplifying `0 * %poison` to the constant `0`). When the expander reuses the original IR instruction sequence to materialize the simplified SCEV expression, it inadvertently injects hidden poison dependencies into new contexts. Furthermore, the mitigation strategy of stripping poison-generating flags (`nsw`, `nuw`) only from the *root* of the reused instruction tree is insufficient, as it fails to clear poison originating from operands or deeper instructions.

### Pattern 2: Context-Dependent Flag Preservation During Code Motion and Simplification
Transformations that move, reuse, or globally cache instructions and expressions frequently fail to properly manage context-dependent optimization flags. For example, when an instruction is hoisted to a new basic block, or when a dominating instruction is reused to short-circuit hoisting, the compiler retains `nsw` or `nuw` flags that were only proven valid in the original, restricted control-flow context. Similarly, when simplifying finite loop non-strict predicates (e.g., `X <= Y` to `X < Y + 1`), the compiler attaches no-wrap flags to the new expression and caches it globally. Because these expressions are now evaluated in broader contexts where the original no-wrap guarantees do not hold, they generate unexpected poison values at runtime.

### Pattern 3: Incomplete Cache Invalidation for Implicit or Scope-Specific Dependencies
The SCEV cache invalidation mechanism relies heavily on explicit IR use-def chains, which handles structural CFG modifications poorly when implicit dependencies exist. When a trivial LCSSA PHI node is analyzed, SCEV looks through it and caches the underlying loop-defined expression in internal structures (like Backedge Taken Counts). If a loop transformation adds a predecessor and makes the PHI non-trivial, the IR-level invalidation fails to clear these internal SCEV caches, leaving stale data. A similar failure occurs with "unanalyzable" instructions (like loads) that have loop-dependent operands; if these operands resolve to constants at a specific scope, the instruction creates a hidden dependency. The invalidation logic assumes unanalyzable instructions act as opaque barriers and stops propagating, resulting in stale cache usage.

### Pattern 4: Flawed Dominance and Iteration Context Reasoning for Loop Variables
The optimization pass struggles to correctly reason about the state of loop-variant values across different iterations. When simplifying conditions at merge points, the compiler incorrectly assumes that because an induction variable's definition location dominates the merge point, its value is safe to use for static implication. It fails to recognize that the evaluated value changes per iteration. Similarly, when analyzing PHI nodes that receive backedge values from the previous iteration, the compiler evaluates the incoming value in the context of the loop latch (where the current iteration's constraints apply) rather than the loop header. This mismatch in iteration contexts leads to invalid simplifications, such as folding conditional checks to constants based on stale or future states.

### Pattern 5: Unsafe Assumptions in Loop Bounds and Exit Condition Simplification
The compiler frequently makes overly aggressive or flawed assumptions when simplifying loop exit conditions and bounds. For zero-stride recurrences, it assumes the loop is infinite (and thus invokes UB) without first verifying if the initial value already satisfies the exit condition, leading to aggressive and incorrect loop elimination. When evaluating truncated loop exit counts, it erroneously elides unsigned overflow checks simply because the induction variable starts at zero and has a positive step, ignoring the fact that truncation can strip significant bits or hide wrap-around. Additionally, when modeling loops with conditionally executed faulting operations (like division), it uses sequential expressions but fails to preserve the protective guards during IR expansion, introducing UB into the optimized program.
