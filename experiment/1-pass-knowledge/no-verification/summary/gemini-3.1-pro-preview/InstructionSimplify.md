# Subsystem Knowledge for InstructionSimplify
## Elements Frequently Missed

*   **Pointer Provenance**: The optimization pass frequently misses the distinction between pointer address equality and pointer provenance. It incorrectly assumes that if two pointers compare equal (`icmp eq`), they are strictly equivalent and can be substituted, which leads to the loss or alteration of provenance information required for memory alias analysis.
*   **Dynamic Masking of Undefined Behavior**: When evaluating operations (like division or remainder) against constant vectors in a `select` instruction, the pass misses the fact that `undef` or zero elements might be dynamically masked out by the `select` condition at runtime. Eagerly folding these to `poison` introduces miscompilations.
*   **Strict Undef-to-Poison Refinement Rules**: The pass misses the strict refinement hierarchy between `undef` and `poison`. It incorrectly assumes that a PHI node with a mix of `undef` and a common value can be folded to the common value, failing to recognize that if the common value is potentially `poison`, this transformation illegally upgrades `undef` to the more restrictive `poison` state.
*   **Partial `undef` Vector Lanes in Logical Identities**: The pass frequently misses that vector constants containing `undef` lanes do not strictly satisfy logical identities. For example, an all-ones vector with `undef` lanes does not behave as a strict bitwise NOT for those specific lanes, breaking the fundamental identities required for logical folds.
*   **Correct Context Instructions for PHI Edges**: When threading operations over PHI nodes, the pass misses the necessity of using the incoming block's terminator as the context instruction. It incorrectly uses the binary operation's own context, erroneously applying control-flow facts (like loop exit conditions) to isolated incoming paths where those facts do not hold.
*   **Zero Edge-Cases in Power-of-Two Math**: The pass misses the `X == 0` edge case when optimizing bitwise operations based on power-of-two assumptions. It incorrectly assumes `X - 1` always forms a contiguous lower-bit mask, failing to account for the fact that if `X` is zero, `X - 1` evaluates to `-1` (all ones), which completely changes the bitwise intersection logic.
*   **Cross-Lane Vector Operations**: The pass misses the cross-lane nature of certain instructions, such as `bitcast` instructions that change the number of vector lanes. It incorrectly assumes that per-lane equivalences (derived from vector `select` conditions) can be propagated through these instructions, breaking the per-lane semantics.
*   **Memory Padding Bits**: When constant-folding loads from memory, the pass misses the distinction between valid bits and padding bits for non-byte-aligned types (e.g., `i9`). It incorrectly assumes the entire memory representation, including uninitialized or zero-extended padding bits, shares the uniform pattern of the constant.
*   **Secondary Results in Multi-Return Intrinsics**: The pass misses that multi-return operations (like structs containing a normalized value and a scale/exponent) are not fully idempotent. It incorrectly assumes that because the primary result is idempotent, the entire operation can be folded, ignoring that the secondary result changes upon repeated application.

## Patterns Not Well Handled

### Pattern 1: Threading Operations Over Control Flow (Select/PHI)
The optimization pass struggles with threading binary operations, divisions, or remainders over control flow instructions like `select` and `phi`. When attempting to evaluate the operation independently for each incoming value or select arm, the pass often fails to correctly adjust the execution context or account for dynamic masking. For `phi` nodes, it applies the merged context of the operation to isolated incoming paths, leading to spurious common values based on conflicting assumptions. For `select` instructions, it eagerly evaluates operations against masked-out constants, unconditionally folding undefined behavior (like division by zero) to `poison` even when that path would never be taken at runtime.

### Pattern 2: Vector Equivalence and Identity Folding with Irregular Lanes
The pass frequently mishandles vector simplifications when lanes are not uniform or strictly independent. It attempts to apply scalar logical identities or per-lane equivalences to vector operations but fails to account for irregularities. For instance, it applies strict bitwise NOT logical folds to vectors containing partial `undef` lanes, which breaks the required logical identity. Similarly, it propagates per-lane equivalences through vector def-use chains without recognizing that instructions like lane-changing `bitcast`s mix data across lanes, thereby invalidating the per-lane equivalence assumption and leading to incorrect folds.

### Pattern 3: Invalid Value Refinement and Substitution
The pass aggressively substitutes values based on equality or commonality but does not well handle the strict rules of value refinement and provenance in LLVM IR. It substitutes pointers based purely on address equality, stripping or altering crucial provenance information needed by the memory model. Furthermore, it folds PHI nodes by ignoring `undef` inputs in favor of a common value, failing to recognize that if the common value can evaluate to `poison`, the transformation illegally makes the program more undefined. These patterns show a systemic issue in respecting the boundaries of valid IR refinement.

### Pattern 4: Over-Assumptions in Mathematical and Memory Properties
The pass makes overly broad assumptions about the properties of values, memory, and intrinsics, failing to handle edge cases. It assumes that an expression like `X - 1` always behaves as a lower-bit mask if `X` is known to be a power of two *or zero*, completely mishandling the zero case. It assumes that memory initialized with a uniform constant maintains that uniform pattern across padding bits, leading to incorrect constant folding on big-endian targets. Finally, it assumes that multi-return intrinsics are fully idempotent based solely on their primary return value, incorrectly folding away secondary computations that are expected to change upon repeated application.
