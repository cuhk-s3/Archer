# Subsystem Knowledge for FunctionAttrs
## Elements Frequently Missed

* **The Absence of the `inbounds` Keyword on `getelementptr` (GEP) Instructions**: The analysis frequently misses the semantic difference between `inbounds` and non-`inbounds` pointer arithmetic. It overlooks the fact that without `inbounds`, pointer arithmetic can wrap around the address space or use negative offsets to explicitly compute a null pointer.
* **Pointer Provenance Translation Across Call Boundaries**: The pass misses the contextual shift of pointer origins between callers and callees. Specifically, it fails to recognize when a pointer that is an argument in the callee actually originates from a non-argument source (like a global variable, local allocation, or loaded pointer) in the caller.
* **Intra-SCC Call Memory Effects**: The analysis optimistically ignores the memory effects of calls within the same Strongly Connected Component (SCC). It misses the necessary validation step to ensure that the pointers being passed to the intra-SCC call maintain the same memory classification (e.g., argument memory vs. global memory) as they do in the caller's context.
* **Address Space Wrap-around Semantics**: The pass frequently misses the edge cases of integer/pointer math where deriving a new pointer from a strictly `nonnull` base pointer can still result in a null address due to arithmetic overflow or underflow.

## Patterns Not Well Handled

### Pattern 1: Optimistic Intra-SCC Memory Attribute Deduction with Context Shifts
This pattern occurs when functions within the same Strongly Connected Component (SCC) pass non-argument pointers (such as pointers loaded from memory, derived from globals, or created via local allocas) to each other. The `FunctionAttrs` pass uses an optimistic interprocedural analysis that assumes the memory effects of intra-SCC calls are strictly bounded by the overall effects of the SCC. Because it ignores the intra-SCC call, it fails to translate the memory locations between the caller and callee. Consequently, if the callee accesses memory through its arguments, the analysis incorrectly assumes the caller is only accessing "argument memory" (`argmemonly`), completely missing the fact that the passed pointer was a "non-argument" pointer in the caller's context. This leads to overly restrictive memory attributes and subsequent invalid optimizations.

### Pattern 2: Unconditional Propagation of Pointer Attributes Through Arithmetic
This pattern involves the compiler tracing a returned or derived pointer back to its source to infer attributes like `nonnull`. When the analysis encounters a `getelementptr` instruction without the `inbounds` restriction, it incorrectly assumes that any pointer derived from a known `nonnull` base pointer inherently remains `nonnull`. It fails to handle the high-level pattern of unrestricted pointer arithmetic, where negative offsets or address space wrap-arounds can legally compute a null address (address zero) from a non-null base. By unconditionally propagating the `nonnull` attribute through non-inbounds arithmetic, the pass tricks downstream optimizations into making false guarantees, leading to the erroneous removal of null checks or other aggressive miscompilations.
