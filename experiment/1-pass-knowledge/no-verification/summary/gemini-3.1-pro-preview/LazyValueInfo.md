# Subsystem Knowledge for LazyValueInfo
## Elements Frequently Missed

* **`undef` and `poison` Values**: These values are frequently mishandled when they appear as incoming values in PHI nodes or as conditions in `select` instructions. The analysis often fails to account for their non-deterministic nature, incorrectly assuming they conform to the restricted ranges of other operands or ignoring them entirely during range intersections.
* **UB-Implying Attributes (`noundef`, `dereferenceable`, `dereferenceable_or_null`)**: These attributes are missed during the safety checks for the speculative evaluation of call instructions. The analysis checks if the callee is speculatable (i.e., lacks side effects) but overlooks attributes that can escalate `undef` or `poison` results into immediate undefined behavior.
* **Non-Deterministic Evaluation of `select` Conditions**: The analysis misses the fact that an `undef` or `poison` condition in a `select` instruction breaks the logical implication between the condition's constraints and the selected data operand, leading to unsound assumptions about the selected value.

## Patterns Not Well Handled

### Pattern 1: Speculative Evaluation of Calls with UB-Implying Attributes
The optimization pass attempts to refine values on specific control-flow edges by speculatively evaluating speculatable calls (e.g., math intrinsics) using edge-specific constraints (like known constants or ranges). However, the safety check for this speculative execution only verifies that the function has no side effects or memory dependencies. It completely fails to handle UB-implying attributes (such as `noundef`) attached to the call's return value or arguments. If the substituted edge-specific operands logically result in `undef` or `poison`, the ignored attributes escalate this to undefined behavior within the analysis's internal reasoning. Consequently, the pass deduces false constraints (e.g., assuming valid execution paths are unreachable) and applies invalid optimizations, such as incorrectly attaching `nsw`/`nuw` flags or restrictive `!range` metadata.

### Pattern 2: Range Inference from `select` Instructions with Potentially `undef`/`poison` Conditions
The pass infers constraints on a `select` instruction's result or its data operands by assuming that the condition must strictly evaluate to `true` or `false` for a specific branch to be chosen. It then intersects the value ranges of the true/false operands with the constraints derived from this condition. This pattern is not well handled because it assumes the condition is always well-defined. If the condition is `undef` or `poison`, it can non-deterministically evaluate to either boolean state at runtime, meaning a branch might be chosen even if the underlying variables do not satisfy the condition's constraints. By relying on this unreliable condition, the analysis deduces overly restrictive and unsound constant ranges, leading to miscompilations such as the improper elimination of bounds checks or incorrect conversions of sign-extensions (`sext`) to zero-extensions (`zext`).

### Pattern 3: Constant Range Computation for PHI Nodes Merging Bounded and `undef` Values
When computing the constant range of a PHI node (or similar merging construct), the analysis evaluates and merges the ranges of its incoming values. A high-level pattern that is poorly handled occurs when one incoming value has a restricted, bounded range (e.g., a zero-extended variable) and another incoming value is explicitly `undef`. Instead of correctly recognizing that `undef` can represent any possible value of that type (which should result in a full, unrestricted range), the analysis incorrectly ignores the `undef` or assumes it conforms to the narrow range of the bounded value. This yields an artificially narrow constant range for the PHI node. Downstream optimization passes then rely on this flawed assumption to erroneously remove necessary instructions, such as bitwise masking operations or conditional branches checking the value's bounds.
