## Test Strategies

### Strategy 1: SIToFP/UToFP with sign bit in middle of truncated bits

- **Target**: Test cases with SIToFP/UToFP where sign bits are in the middle of bits that would be truncated by minbitwidth analysis
- **Rationale**: The fix checks if NumSignBits * 2 >= type size to decide if operand can be truncated. However, for SIToFP/UToFP, the sign bit semantics are different - the sign bit determines whether the integer is interpreted as signed or unsigned, not just the high bits. If we truncate bits that include the sign bit position but not all high bits, we could change the sign interpretation.
- **Expected Issue**: Incorrect floating-point values after vectorization due to sign bit truncation changing signedness interpretation

### Strategy 2: ICmp with mixed signed/unsigned predicates on truncated operands

- **Target**: ICmp instructions with mixed signed/unsigned predicates (e.g., slt, ult) where operands get truncated
- **Rationale**: The fix checks sign bits for ICmp operands but doesn't consider predicate signedness. For unsigned comparisons (ult, ule, ugt, uge), the sign bit is irrelevant, but the fix might incorrectly prevent truncation. For signed comparisons, truncating sign bits is always wrong.
- **Expected Issue**: Incorrect comparison results after vectorization due to improper truncation of sign bits for signed comparisons or missed optimization for unsigned comparisons

### Strategy 3: DemandedBits analysis mismatch for SIToFP/UToFP operands

- **Target**: Cases where DemandedBits analysis returns incomplete mask for SIToFP/UToFP operands
- **Rationale**: The fix uses DB->getDemandedBits() for instruction operands of SIToFP/UToFP, but DemandedBits may not track demanded bits for floating-point conversion operands correctly, potentially returning incomplete masks.
- **Expected Issue**: Incorrect truncation decisions based on incomplete demanded bits information, leading to wrong floating-point conversions

### Strategy 4: ExtraBitWidthNodes insertion with out-of-bounds indices

- **Target**: Edge cases where ExtraBitWidthNodes.insert() is called with indices beyond VectorizableTree size
- **Rationale**: The fix inserts VectorizableTree.size() + 1 for trunc nodes and getOperandEntry(TE, 0/1)->Idx for ICmp operands. If the tree is resized or reordered, these indices might become invalid or point to wrong entries.
- **Expected Issue**: Crash or incorrect minbitwidth analysis due to invalid indices in ExtraBitWidthNodes set

### Strategy 5: Mixed SIToFP and UIToFP in same vectorization bundle

- **Target**: Vectorization bundles containing both SIToFP and UIToFP instructions
- **Rationale**: The fix handles SIToFP and UIToFP separately but doesn't consider mixed bundles. If a bundle contains both, the sign bit analysis needs to be conservative for the worst case (SIToFP).
- **Expected Issue**: Incorrect truncation for UIToFP operands when mixed with SIToFP, or missed optimization for SIToFP when mixed with UIToFP

## Bugs Found

### Bug #1

**Analysis:**
The difference is a real bug, not UB. Original scalar code: %t1 = trunc i32 %a to i8 (0xFF), %s1 = sext i8 %t1 to i32 (0xFFFFFFFF = -1 interpreted as unsigned 4294967295), %u1 = uitofp i32 %s1 to float -> 2^32 = 0x4F800000 (high16 = 0x4F80, exit code 0x80 = 128). The SLP-vectorized version drops the sext and emits `uitofp <2 x i8> %2 to <2 x float>`, which zero-extends the i8 lane 0xFF -> 255.0f = 0x437F0000 (high16 = 0x437F, exit code 0x7F = 127). No undefined behavior in the original (all values defined, in-bounds global accesses), so the differing results are a genuine miscompile. It is caused by the new ExtraBitWidthNodes seeding for UIToFP: the sext operand node is registered as a new minbitwidth root and demoted to i8 (MinBWs IsSigned=true), but in vectorizeTree the cast case skips the SrcIt/It adjustment when the result type is floating point, so the uitofp is emitted directly on the narrowed <2 x i8> vector, changing the value semantics (sign-extended-then-unsigned-convert vs zero-extend of the truncated value).
