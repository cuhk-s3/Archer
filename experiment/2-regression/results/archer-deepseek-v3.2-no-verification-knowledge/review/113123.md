## Test Strategies

### Strategy 1: Fast-Math Flags Intersection

- **Target**: Fast-math flags on fcmp instructions
- **Rationale**: The patch unions FMFs from both fcmp instructions (LHS->getFastMathFlags() | RHS->getFastMathFlags()). This could incorrectly propagate flags like 'nnan' or 'ninf' from one comparison to the combined fabs+fcmp, potentially introducing poison where none existed before.
- **Expected Issue**: Union of FMFs may be overly restrictive, causing valid NaN/Inf values to become poison in the transformed code.

### Strategy 2: Undef Handling in Vector Constants

- **Target**: Vector constants with undef elements
- **Rationale**: The patch uses m_APFloatAllowUndef which allows undefs in splat vector constants. However, the transformation creates fabs(x) and compares it with a constant. If the original constants had undef elements, the new constant may not preserve the same undef semantics.
- **Expected Issue**: Undefined behavior or incorrect results when vector constants contain undef elements.

### Strategy 3: Signed Zero Semantics

- **Target**: Comparisons involving -0.0 and +0.0
- **Rationale**: The transformation uses fabs which discards sign information. For comparisons like fcmp olt x, C and fcmp ogt x, -C where C is 0.0, the sign of zero matters. fabs(-0.0) = +0.0, which could change comparison results.
- **Expected Issue**: Incorrect transformation when C is 0.0 and x is -0.0.

### Strategy 4: Predicate Swapping Logic

- **Target**: Order of predicates in AND/OR operations
- **Rationale**: The code swaps predicates and constants based on IsLessThanOrLessEqual(IsAnd ? PredR : PredL). This logic may incorrectly handle edge cases where both predicates are 'less than' variants or when the operation is OR instead of AND.
- **Expected Issue**: Incorrect predicate selection leading to wrong comparison semantics.

### Strategy 5: NaN Propagation in fabs

- **Target**: NaN values with sign bits
- **Rationale**: fabs preserves NaN payload but clears sign bit. The transformation assumes fabs(x) olt/ole/ult/ule C is equivalent to the original range check, but for signaling NaNs with sign bits, this could affect unordered comparisons.
- **Expected Issue**: Different behavior for signaling NaNs with negative sign in unordered comparisons.

### Reproducer

**LLVM IR:**

define i1 @test_fmf_union_bug_zero(float %x) {
  %cmp1 = fcmp nnan olt float %x, 0.0
  %cmp2 = fcmp ogt float %x, -0.0
  %cond = and i1 %cmp1, %cmp2
  ret i1 %cond
}

define i1 @main() {
  %r = call i1 @test_fmf_union_bug_zero(float 0x7FF8000000000000)
  ret i1 %r
}

### Analysis

Bug Triggering Analysis: This is another instance of the same bug with C=0.0. The patch unions FMFs, adding 'nnan' to result. With NaN input: original returns poison (first comparison with 'nnan' returns poison, second returns false, AND of poison and false = poison). Transformed returns false (no poison). This shows the bug exists even with zero constants.

Fix Weakness Analysis: The FMF union issue is fundamental to the patch design. The transformation should use intersection of FMFs (LHS->getFastMathFlags() & RHS->getFastMathFlags()) rather than union, to preserve only assumptions common to both original comparisons. Union adds new assumptions that can change poison semantics.
