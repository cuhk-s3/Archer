## Test Strategies

### Strategy 1: S1: Apply injected condition across a loop PHI incoming edge (dynamic-instance conflation)

- **Target**: A select-inside-a-loop test (e.g. mutate llvm/test/Transforms/InstCombine/known-phi-br.ll / select.ll cases) shaped as:
  entry: br label %loop
  loop:
    %p = phi i8 [ 5, %entry ], [ %v, %loop ]
    %v = add i8 %p, 1
    %c = icmp eq i8 %v, 5
    %s = select i1 %c, i8 %p, i8 0
    (make %s observable: store to a global / return it; trip count large enough that %v wraps to 5)
The arm %p is not itself affected, but its backedge incoming %v is in CondContext::AffectedValues, so hasAffectedValue() returns true (PHI special-case sets Depth = MaxAnalysisRecursionDepth-2) and computeKnownBits(%p) intersects the entry incoming (const 5) with the backedge incoming computed at RecQ.CxtI = backedge terminator, where computeKnownBitsFromContext injects the select condition and yields const 5.
- **Rationale**: The new branch in computeKnownBitsFromContext has no context/dominance validity check (unlike the DomConditionCache path, which uses Q.DT->dominates(Edge, Q.CxtI->getParent())). Recursive computeKnownBits calls for PHI incomings and for matchSimpleRecurrence step values copy Q (thus CC) but change CxtI to a different program point, where the SSA value denotes a different loop iteration's dynamic instance. The fact 'cond is true at the select' says nothing about %v at the backedge of the previous iteration.
- **Expected Issue**: The true arm is folded to the wrong constant (5 instead of the actual 4 for the iteration in which the condition holds) -> silent miscompile; CHECK lines would show 'select i1 %c, i8 5, i8 0'. A CEGAR/interpreter-style differential test (or just hand-evaluating the loop) shows the optimized IR differs from the original for a live, non-poison execution.

### Strategy 2: S2: Wrong-polarity / arm-asymmetry check for the Invert flag

- **Target**: Take a fold-positive test (condition 'icmp eq i8 %x, 3' with an affected value inside the TRUE arm) and (a) swap the arms so that only the FALSE arm contains the affected value, (b) use a non-commutative predicate (slt/ugt) and a non-equality predicate so that getInversePredicate() must be applied, (c) use a logical-and/or condition ('and i1 %a,%b', 'or i1 %a,%b', and the poison-blocking 'select i1 %a, i1 %b, i1 false' form that m_LogicalOp also matches) where Invert flips unionWith<->intersectWith.
- **Rationale**: The fold mutates one shared CondContext (CC.Invert = true) and re-uses the same SimplifyQuery for the false arm; the union/intersect choice inside computeKnownBitsFromCond depends on both Invert and the matched logical form. Any leak of Invert=false state into the false-arm query (or an inverted union/intersect) yields bits implied by the *other* branch.
- **Expected Issue**: The false arm is folded to a constant implied by the true branch (or vice versa), i.e. an incorrect constant operand; for 'or'-conditions the union-instead-of-intersect case would report a constant although only one disjunct holds.

### Strategy 3: S3: Conflicting KnownBits from an unsatisfiable condition (no hasConflict() guard)

- **Target**: Conditions that contradict the arm's structural known bits, e.g. '%and = and i8 %x, 15; %c = icmp eq i8 %and, 16; %r = and i8 %and, 16; %s = select i1 %c, i8 %r, i8 0', plus variants where the contradiction is only reachable through a nested value, through a splat vector, or through a PHI (one incoming conflicting, the other not). Also variants where the conflicting value is the arm's operand feeding an 'add'/'or' so that KnownBits::computeForAddSub propagates the conflict.
- **Rationale**: KnownBits::isConstant() only checks Zero.popcount()+One.popcount()==BitWidth, so an overlapping Zero/One pair (e.g. i2 Zero=0b01,One=0b01) is reported as 'constant' and getConstant() returns One, which contradicts Zero. computeKnownBitsFromContext resets conflicts only inside the DC/AC blocks, and the new injected-cond branch is not itself guarded; the existing Select case in computeKnownBitsFromOperator explicitly checks CondRes.hasConflict() and isGuaranteedNotToBeUndef(), showing the author considered this hazard elsewhere but not in the new path.
- **Expected Issue**: The arm is replaced by an arbitrary constant (e.g. 0 where the condition implies 16), or valid operator-derived bits are silently discarded by the conflict reset causing inconsistent fold/no-fold behaviour between the two arms; in the worst case an unexpected constant is produced for a live path if the conflict comes from an unsound sub-analysis rather than from dead code.

### Strategy 4: S4: Gate (hasAffectedValue) vs analysis (computeKnownBits) traversal mismatch

- **Target**: Arms whose operand graph reaches the affected value only through edges the gate ignores but the analysis walks through: 'freeze i8 %x', 'bitcast'/'ptrtoint'/'inttoptr', 'fptosi'/'fptoui', 'extractelement'/'insertelement'/'shufflevector' with poison lanes, i1/i1-vector edges, ConstantExpr operands, and a pointer-typed affected value ('%c = icmp eq i64 %p2i, 0' with '%p2i = ptrtoint ptr %p to i64') combined with a second operand that does pass the gate. Also arms where the affected value is only at Depth==0 (the arm itself) or behind a GEP/pointer chain.
- **Rationale**: hasAffectedValue is only a heuristic pre-filter (it stops at non-int operands and skips the Depth==0 hit), while computeKnownBits with the injected CC traverses pointer/bitcast/freeze paths and applies pointer-specific rules (Known.setAllZero() for icmp-eq-null, m_PtrToIntSameSize, m_ElementWiseBitCast/float affected values inserted by findValuesAffectedByCondition). The two traversals disagreeing means the fold can be driven by information the gate never validated, or by APInts of a different bit width than Known (unionWith asserts equal widths).
- **Expected Issue**: Either missed folds (optimization gap that should be documented), or a wrong/oversized constant (e.g. folding a ptrtoint-derived arm using pointer-null bits) and, in the mismatched-width case, an APInt bit-width assertion failure / verifier error on the produced ConstantInt type.

### Strategy 5: S5: Vector, i1 and scalable-vector arm constant construction

- **Target**: Mutate a scalar fold test into: (a) fixed vector with a splat condition ('icmp eq <2 x i8> %x, <i8 3, i8 3>'), (b) fixed vector with a NON-splat condition ('<i8 3, i8 4>'), (c) scalar i1 condition selecting vectors ('select i1 %c, <2 x i8> %v, ...'), (d) vector condition with poison/undef lanes in the arm ('<2 x i8> <i8 3, i8 poison>', shuffle with poison mask), (e) scalable vector '<vscale x 2 x i8>', (f) i1 / <N x i1> select arms, (g) an arm whose lanes are constrained only in *some* lanes (extractelement-based condition).
- **Rationale**: computeKnownBits returns element-width KnownBits that are the intersection over demanded lanes, while the fold builds 'ConstantInt::get(SelType, Known.getConstant())', which broadcasts a single element value to every lane (ConstantVector::getSplat / ConstantInt with vector type). For vector conditions m_APInt only matches splats, and for i1 arms isConstant() is satisfied by a single known bit. The patch has no i1 exclusion (unlike the neighbouring select C,1,0 -> zext fold) and no lane-wise check.
- **Expected Issue**: A lane-dependent constraint being broadcast as a splat constant to all lanes (wrong values for undemanded/unconstrained lanes), an incorrectly typed constant (ConstantInt vs ConstantVector vs scalable-vector splat ConstantExpr) triggering a verifier failure, or an unsound i1 fold.

### Strategy 6: S6: Compile-time cost / repeated work on pathological select graphs

- **Target**: Stress tests: (a) many selects sharing one deep/wide operand graph (long add/and chains, wide <N x i64> vectors) where the gate passes but no fold results, (b) nested/mutually-referential loop PHIs (several phis in a row) so that hasAffectedValue's PHI depth reset is repeatedly triggered, (c) conditions that are deep logical-and/or trees of icmps (findValuesAffectedByCondition worklist + AffectedValues growth), (d) a select whose arms are re-visited many times by the InstCombine worklist (each replaceOperand re-adds SI).
- **Rationale**: The commit message itself motivates the AffectedValues pre-computation because 'computeKnownBits() is expensive in pathological cases', but the remaining cost centres are unbounded: hasAffectedValue walks the whole operand DAG of both arms with no use-count/memoization limit and is invoked on every visitSelectInst, findValuesAffectedByCondition runs before the AffectedValues.empty() check, and the fold runs after all other select folds (so it is reached for every select that survives canonicalization).
- **Expected Issue**: Quadratic/exponential compile-time growth (visible with -time-passes or a -Rpass=instcombine timing test), and potentially repeated re-visiting of the same select after each successful arm replacement; no functional miscompile but a scalability regression that a maintainer would want covered by a test.

## Bugs Found

### Bug #1

**Analysis:**
The difference is a real miscompile. The original loop computes: p=5,s=1 -> v=5^1=4 (cond false, sel=0); p=4,s=2 -> v=4^2=6 (false, sel=0); p=6,s=3 -> v=6^3=5 (TRUE, sel=p=6); ... The optimized IR replaced the true arm %p with the constant 5 because computeKnownBits(%p) intersected the entry incoming (constant 5) with the backedge incoming %v, where the *injected select condition* (icmp eq i8 %v, 5) was applied. But %v at the backedge terminator is the value of the NEXT iteration, not the one the select condition constrains. Both programs are entirely UB-free (defined i8 arithmetic, no poison, terminating loop), and they return different values (32 vs 60), so this is a genuine miscompile introduced by the new CondContext handling in computeKnownBitsFromContext (no context/dominance validity check for the injected condition when recursion crosses a PHI incoming edge).

**Original LLVM IR:**
```llvm

define i8 @S1_phi_loop() {
entry:
  br label %loop

loop:
  %p = phi i8 [ 5, %entry ], [ %v, %loop ]
  %s = phi i8 [ 1, %entry ], [ %s.next, %loop ]
  %acc = phi i8 [ 0, %entry ], [ %acc.next, %loop ]
  %s.next = add i8 %s, 1
  %v = xor i8 %p, %s
  %c = icmp eq i8 %v, 5
  %sel = select i1 %c, i8 %p, i8 0
  %acc.next = add i8 %acc, %sel
  %exitcond = icmp eq i8 %s, 50
  br i1 %exitcond, label %exit, label %loop

exit:
  ret i8 %acc.next
}

define i8 @main(i32 %argc, ptr %argv) {
entry:
  %r = call i8 @S1_phi_loop()
  ret i8 %r
}

```
