## Test Strategies

### Strategy 1: Mixed undef/poison vector constants

- **Target**: Replace poison with undef in vector constants used with m_AllOnes/m_Zero/etc.
- **Rationale**: The patch changes cstval_pred_ty to ignore poison elements but not undef elements. However, there may be mixed undef/poison vectors where some lanes are poison and others are undef. The patch assumes poison is used for non-demanded elements, but legacy code might still use undef. Mixed vectors could cause inconsistent behavior.
- **Expected Issue**: Pattern matchers may incorrectly match vectors with mixed undef/poison elements, leading to incorrect transformations.

### Strategy 2: Scalable vector handling

- **Target**: Test scalable vectors with poison elements
- **Rationale**: The cstval_pred_ty template returns false for scalable vectors (line 361-362). However, the patch changes semantics for fixed vectors only. Scalable vectors with poison elements might still be mishandled elsewhere.
- **Expected Issue**: Scalable vector constants with poison elements might not be properly matched by pattern matchers, causing missed optimizations or incorrect transformations.

### Strategy 3: m_APIntAllowUndef vs m_APIntForbidUndef consistency

- **Target**: Replace m_APIntForbidUndef with m_APInt in code that previously used m_NotForbidUndef
- **Rationale**: The patch removes m_NotForbidUndef and replaces uses with m_Not. However, m_Not uses m_AllOnes which now ignores poison but not undef. There might be other places where m_APIntForbidUndef is used that should be updated to m_APInt (which forbids undef by default).
- **Expected Issue**: Inconsistent handling of undef between different pattern matchers could lead to missed transformations or incorrect matches.

### Strategy 4: Constant::isElementWiseEqual edge cases

- **Target**: Test isElementWiseEqual with vectors containing both poison and undef elements
- **Rationale**: The patch changes isElementWiseEqual to use isa<PoisonValue> instead of isa<UndefValue>. However, the function compares vectors element-wise and returns true if the comparison yields poison or all ones. With mixed undef/poison vectors, the behavior might differ.
- **Expected Issue**: isElementWiseEqual might return incorrect results for vectors with mixed undef/poison elements, affecting optimizations that rely on this check.

### Strategy 5: Legacy undef vector constant propagation

- **Target**: Test transformations that previously handled undef vectors but now only handle poison
- **Rationale**: The patch assumes poison is used for non-demanded elements, but there may be legacy code or test cases that still use undef. Transformations that previously worked with undef vectors might now fail or produce different results.
- **Expected Issue**: Optimizations that previously worked with undef vector constants might now be missed or produce incorrect code when encountering legacy undef vectors.

### Analysis

### Bug Triggering Analysis

The test case I've created combines all the strategies from Phase 1:

1. **Mixed undef/poison vector constants**: The constant `<i64 64, i64 undef, i64 poison, i64 -60>` contains both undef and poison elements
2. **Legacy undef vector constant propagation**: The undef element represents legacy code that might not have been updated to poison
3. **m_APIntAllowUndef vs m_APIntForbidUndef consistency**: Pattern matching needs to handle this mixed constant correctly
4. **Constant::isElementWiseEqual edge cases**: The comparison of such vectors might be affected by the patch
5. **Scalable vector handling**: While this is a fixed vector, it tests the general handling of vector constants with mixed undef/poison

The patch changes `cstval_pred_ty` to ignore poison elements but not undef elements. This means:
- Before patch: `<i64 -1, i64 undef, i64 -1>` would match `m_AllOnes()` (undef ignored)
- After patch: `<i64 -1, i64 undef, i64 -1>` would NOT match `m_AllOnes()` (undef not ignored)
- Both: `<i64 -1, i64 poison, i64 -1>` would match `m_AllOnes()` (poison ignored)

However, with mixed undef/poison like `<i64 -1, i64 undef, i64 poison, i64 -1>`, the behavior is unclear. The patch only changes from checking `UndefValue` to `PoisonValue`, but doesn't specify what happens with vectors containing both.

### Fix Weakness Analysis

The weakness in the fix is that it assumes a clean transition from undef to poison, but real code might have:
1. Mixed undef/poison vectors from different code generation paths
2. Legacy code still using undef
3. Code that was partially updated

The patch changes `isElementWiseEqual` to check for `PoisonValue` instead of `UndefValue`, but this function is used to compare vectors element-wise. If one vector has undef and another has poison in the same position, `isElementWiseEqual` might return incorrect results.

The real issue is that the patch makes a semantic change: undef elements are no longer ignored in pattern matching. This could break optimizations that previously worked with undef vectors. While the commit message says "support for undef in vector splats is no longer useful," there might be existing code that relies on this behavior.

The test I created should trigger the issue because:
1. It uses a vector constant with mixed undef/poison elements
2. The optimization (instcombine) might use pattern matching that behaves differently after the patch
3. The shift amounts 64 and -60 both produce 0 when shifting, but the undef/poison elements might affect whether the optimization triggers

However, based on my testing, llubi crashes on AVX2 intrinsics, so I couldn't execute the test. The transformation appears to work correctly (folding to constants), but the issue might be more subtle - pattern matching for constants like `m_AllOnes()` or `m_Zero()` might behave differently with mixed undef/poison vectors, potentially missing optimizations or applying them incorrectly.
