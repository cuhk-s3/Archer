## Test Strategies

### Strategy 1: Vector Constant Sign Bit Edge Cases

- **Target**: Vector constants with mixed sign bits and undef elements
- **Rationale**: The vector constant handling in computeKnownFPClass sets SignBit = SignBitAllOne when SignBitAllOne != SignBitAllZero. This could incorrectly set SignBit to true when all non-undef elements are positive (SignBitAllOne = false, SignBitAllZero = true). The condition should check if SignBitAllOne is true, not if they're different.
- **Expected Issue**: Incorrect sign bit inference for vector constants with all positive elements and undef elements

### Strategy 2: Min/Max Intrinsic Sign Bit Logic with NaN

- **Target**: minnum/maxnum/minimum/maximum intrinsics with NaN handling
- **Rationale**: The sign bit logic in lines 4598-4617 only applies when Known.isKnownNeverNaN(). However, the earlier code at lines 4546-4547 clears NaN for minnum/maxnum if either operand is not NaN. This creates a race condition where NaN may be cleared but sign bit logic still doesn't apply because Known.isKnownNeverNaN() may not reflect the cleared state.
- **Expected Issue**: Missing sign bit inference for minnum/maxnum when one operand is known never NaN

### Strategy 3: FMul Sign Bit Inference with Mixed Known Bits

- **Target**: FMul with one operand having known sign bit and other unknown
- **Rationale**: Lines 4967-4972 only set sign bit when both operands have known sign bits. However, if one operand has known sign bit (e.g., positive) and the other is known never negative (but sign bit unknown), the result should have known sign bit (positive). The current logic misses this case.
- **Expected Issue**: Missing sign bit inference for multiplication with partially known sign information

### Strategy 4: Copysign Optimization with computeKnownFPSignBit

- **Target**: InstCombine copysign optimization using computeKnownFPSignBit
- **Rationale**: The new computeKnownFPSignBit returns std::optional<bool> where false means sign bit is 0, true means sign bit is 1. The InstCombine code assumes this correctly handles NaN sign bits. However, computeKnownFPSignBit calls computeKnownFPClass with fcAllFlags, which includes NaN. The sign bit for NaN may be arbitrary, so returning true/false for values that could be NaN might be incorrect.
- **Expected Issue**: Incorrect copysign optimization when sign operand could be NaN with arbitrary sign bit

### Strategy 5: Fabs Simplification with computeKnownFPSignBit

- **Target**: InstructionSimplify fabs simplification using computeKnownFPSignBit
- **Rationale**: The fabs simplification at line 6220 uses computeKnownFPSignBit to check if sign bit is zero. If computeKnownFPSignBit returns false (sign bit is 0), it eliminates fabs. However, if the value could be NaN with sign bit 0, fabs should still be eliminated (fabs preserves NaN payload). This is correct but needs verification that computeKnownFPSignBit handles NaN sign bits properly.
- **Expected Issue**: Potential missed fabs elimination for NaN with sign bit 0
