## Test Strategies

### Strategy 1: Undef/Poison Propagation

- **Target**: Select condition and arms with undef/poison values
- **Rationale**: The fix uses computeKnownBits which may propagate undef/poison incorrectly when analyzing select arms under conditional context. If the condition or affected values contain undef/poison, the optimization might incorrectly fold to a constant.
- **Expected Issue**: Incorrect constant folding leading to miscompilation when undef/poison values are involved.

### Strategy 2: Recursion Depth Limit Violation

- **Target**: Deeply nested expressions in select arms
- **Rationale**: hasAffectedValue has recursion depth limits but computeKnownBits also has its own recursion limits. The interaction between these limits might cause incomplete analysis or incorrect results when analyzing complex expressions.
- **Expected Issue**: Incomplete analysis leading to missed optimization opportunities or incorrect transformations.

### Strategy 3: PHI Node Handling

- **Target**: Select arms containing PHI nodes
- **Rationale**: hasAffectedValue has special handling for PHI nodes with Depth = MaxAnalysisRecursionDepth - 2, but this might not align with computeKnownBits' handling of PHI nodes. The interaction could lead to incorrect analysis of values affected by conditions.
- **Expected Issue**: Incorrect constant folding when select arms contain PHI nodes affected by the condition.

### Strategy 4: Vector Type Mismatch

- **Target**: Vector selects with mixed scalar/vector conditions
- **Rationale**: The fix checks SelType->isIntOrIntVectorTy() but doesn't ensure condition and select type vector dimensions match. findValuesAffectedByCondition might not handle vector conditions correctly for all patterns.
- **Expected Issue**: Incorrect analysis leading to wrong constant folding for vector selects.

### Strategy 5: Conflicting KnownBits

- **Target**: Select arms where KnownBits analysis produces conflicting results
- **Rationale**: computeKnownBitsFromCond can produce conflicting KnownBits which are reset. However, the fix doesn't check for conflicts after computing KnownBits with the injected condition context.
- **Expected Issue**: Incorrect constant folding when KnownBits has conflicts that should be reset.

### Analysis

### Bug Triggering Analysis\n\nThe test case `vec_select_no_equivalence` exposes a real bug in the new optimization. When x=<0,2>:\n- Condition: icmp eq <0,2>, <0,0> = <true,false>\n- Shuffle: shufflevector <0,2> -> <2,0>\n- Select: select <true,false>, <2,0>, <0,2> = <2,2> (chooses first element from shuffle when true, second from x when false)\n\nHowever, the optimization incorrectly folds this to just `ret <2 x i32> %x`, which returns <0,2>. This is wrong because the first element should be 2 (from the shuffled vector) not 0.\n\nThe bug occurs because the new optimization uses `findValuesAffectedByCondition` and `computeKnownBits` with injected condition context, but fails to account for the shufflevector operation that reorders elements. The condition implies something about individual elements of x, but the shuffle changes which element goes where.\n\n### Fix Weakness Analysis\n\nThe fix weakness is in the interaction between the new condition context mechanism and operations that reorder or transform vector elements. The optimization assumes that if the condition provides information about x, then operations on x (like shufflevector) can be analyzed under that context. However, shufflevector changes the mapping between input and output elements, so the condition's implications don't directly transfer to the shuffled result.\n\nSpecifically, when analyzing `select(icmp eq x, 0), shuffle(x), x`, the optimization might deduce that when the condition is true for an element, that element of x is 0, and therefore the corresponding element of shuffle(x) is also 0 (since it's just a permutation). But this is incorrect because shuffle swaps elements: if x[0]=0 and x[1]=2, shuffle(x)[0]=2, not 0.\n\nThe fix needs to handle operations that reorder vector elements more carefully when propagating known bits from conditions.
