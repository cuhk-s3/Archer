## Test Strategies

### Strategy 1: Poison-generating flags retention

- **Target**: nsw/nuw flags on srem/add operations
- **Rationale**: The transformation creates new add and and instructions but may incorrectly retain poison-generating flags from original srem/add operations. If the original srem had nsw/nuw flags, they may not be valid for the new add/and operations in the transformed context.
- **Expected Issue**: Poison propagation where previously safe code becomes unsafe due to retained flags.

### Strategy 2: Zero divisor handling

- **Target**: Remainder value being zero (n=0)
- **Rationale**: The code uses isKnownToBeAPowerOfTwo(Remainder, /*OrZero*/ true) which allows zero. However, srem with zero divisor is undefined behavior. The transformation should not apply when n=0, but OrZero=true might allow it.
- **Expected Issue**: Transformation applied to undefined behavior case, potentially creating valid code from invalid.

### Strategy 3: Negative divisor assumption violation

- **Target**: Negative power-of-two divisors
- **Rationale**: The comment says 'divisor is a power of two and is guaranteed not to be negative' but the code only checks isKnownToBeAPowerOfTwo which doesn't guarantee non-negativity. A negative power-of-two divisor (e.g., -8) would break the transformation.
- **Expected Issue**: Incorrect transformation for negative divisors leading to wrong results.

### Strategy 4: Vector element mismatch

- **Target**: Vector types with poison/undef elements
- **Rationale**: The pattern matching uses m_Specific which requires exact match, but vector operations with poison/undef elements might not match correctly. Also, isKnownToBeAPowerOfTwo on vectors might have edge cases.
- **Expected Issue**: Missed optimization or incorrect transformation for vector types.

### Strategy 5: Integer overflow in n-1 calculation

- **Target**: n = INT_MIN (for signed types)
- **Rationale**: When n is the minimum signed integer (e.g., -2147483648 for i32), n-1 overflows. The transformation creates n-1 via CreateAdd(Remainder, Constant::getAllOnesValue(...)). For signed types, this might overflow.
- **Expected Issue**: Integer overflow in constant calculation leading to wrong mask.
