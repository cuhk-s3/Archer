## Test Strategies

### Strategy 1: Missing Signed Variable Non-Negative Constraint

- **Target**: Signed constraint system for new variables
- **Rationale**: The fix adds Var >= 0 constraints for new variables only in the unsigned system, but not in the signed system. This asymmetry could cause missed optimizations when signed comparisons rely on non-negative assumptions.
- **Expected Issue**: Missed optimization for signed comparisons involving new variables that are known to be non-negative

### Strategy 2: Inconsistent Stack Synchronization

- **Target**: DFSInStack synchronization with constraint system
- **Rationale**: The fix adds extra stack entries for Var >= 0 constraints but doesn't properly account for them in the stack synchronization logic, potentially causing stack corruption or incorrect constraint removal.
- **Expected Issue**: Stack corruption or incorrect constraint removal leading to wrong optimization results

### Strategy 3: Overflow in Coefficient Computation

- **Target**: Coefficient computation for Var >= 0 constraints
- **Rationale**: The fix uses -1 coefficient for Var >= 0 constraints. If variable index exceeds coefficient vector bounds or if Value2Index size changes during constraint addition, this could cause out-of-bounds access.
- **Expected Issue**: Out-of-bounds memory access or incorrect constraint representation

### Strategy 4: Missing Precondition Check for Non-Negative Variables

- **Target**: Precondition validation for Var >= 0 constraints
- **Rationale**: The fix assumes all new variables in unsigned system are non-negative, but doesn't verify this precondition. If a variable can be negative, adding Var >= 0 constraint could make the system unsound.
- **Expected Issue**: Incorrect optimization due to unsound constraint system

### Strategy 5: Interaction with Signed System Transfer Logic

- **Target**: transferToOtherSystem function
- **Rationale**: The fix adds Var >= 0 constraints only to unsigned system, but transferToOtherSystem logic might expect symmetric constraints in both systems for proper signed-unsigned transfer.
- **Expected Issue**: Missed transfer opportunities or incorrect transfer results

### Analysis

# Additional Bug Case

This test case `test_n_must_ule_1_due_to_nuw` shows another instance of the same bug pattern. With `%n = 0`, `add nuw i8 0, -1 = 255` (wraps), making `%sub.n.1` negative in signed interpretation. The fix incorrectly adds `%sub.n.1 >= 0` constraint, leading to unsound optimization that changes UB to defined behavior.

# Root Cause Analysis

The fundamental issue is that the patch adds `Var >= 0` constraints for **all** new variables in the unsigned system without checking if they're truly non-negative. For operations like `add nuw` with negative constants, the result wraps and becomes a large unsigned value that's non-negative in unsigned domain, but the constraint system's assumption leads to incorrect deductions.

The fix needs to either:
1. Verify variables are truly non-negative before adding constraints
2. Handle wrapped values correctly in the constraint system
3. Limit the constraint addition to variables known to be non-negative via other means

The current implementation is overly optimistic and unsound.
