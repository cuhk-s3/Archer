## Test Strategies

### Strategy 1: MixedSignednessWithSameSign

- **Target**: Test cases where one icmp has samesign flag and the other doesn't, with mixed signed/unsigned predicates
- **Rationale**: The fix handles XOR of hasSameSign() but may incorrectly handle cases where predicates have different signedness semantics
- **Expected Issue**: Incorrect implication result when one comparison has samesign flag but predicates have different signedness interpretations

### Strategy 2: PoisonPropagationWithSameSign

- **Target**: Test cases where samesign flag introduces poison when operands have different signs
- **Rationale**: The fix doesn't consider that samesign icmp returns poison when operands have different signs, which affects implication logic
- **Expected Issue**: Incorrectly concluding implication when LHS could be poison but RHS wouldn't be

### Strategy 3: VectorTypesWithSameSign

- **Target**: Vector icmp comparisons with samesign flag and mixed element signs
- **Rationale**: Vector comparisons may have elements with different signs, making samesign semantics more complex
- **Expected Issue**: Incorrect implication for vector types where some elements satisfy samesign condition but others don't

### Strategy 4: BoundaryValuesWithSameSign

- **Target**: Test cases with boundary values near signed/unsigned overflow points
- **Rationale**: ConstantRange calculations may behave differently for signed vs unsigned comparisons near boundaries
- **Expected Issue**: Incorrect implication near min/max values when flipping signedness

### Strategy 5: MultipleSameSignFlags

- **Target**: Test cases where both icmps have samesign flag
- **Rationale**: The fix explicitly says 'only case we need to handle is when exactly one of the icmps have samesign' - but what if both have it?
- **Expected Issue**: Missing handling for case where both comparisons have samesign flag

### Analysis

# Bug Triggering Analysis\nThis test exposes a real bug in the fix. When %a = 5 (positive):\n1. `icmp sgt i32 5, -10` = true (signed comparison)\n2. `icmp samesign uge i32 5, -20` = poison (signs differ: 5 is non-negative, -20 is negative)\n3. The `select` returns poison\n\nHowever, the optimization incorrectly transforms this to always return 30. The fix assumes that `samesign uge` can be transformed to `sge` when exactly one comparison has the samesign flag, but it fails to consider that `samesign` introduces poison when operands have different signs, while the transformed predicate (`sge`) does not.\n\n# Fix Weakness Analysis\nThe fix has a fundamental weakness: it treats `samesign P` as equivalent to `flipped-signedness(P)` for implication analysis, but this is incorrect due to poison semantics. When operands have different signs:\n- `samesign P` returns poison\n- `flipped-signedness(P)` returns a boolean result based on the comparison\n\nThis violates the principle that optimizations should not introduce new undefined behavior. The original program might produce poison (which could propagate to undefined behavior), while the optimized program produces a definite value (30). This makes the optimized program more defined than the original, which is incorrect.\n\nThe fix needs to consider the poison-generating nature of the `samesign` flag. When analyzing implications involving `samesign` comparisons, it must account for the fact that the comparison could be poison when operands have different signs, which affects whether one condition implies another.
