## Test Strategies

### Strategy 1: ExtractLane with multiple vector operands and invalid lane index

- **Target**: ExtractLane generation logic in VPlanRecipes.cpp
- **Rationale**: The ExtractLane implementation assumes lane index is within bounds of combined vector operands, but doesn't validate that LaneToExtract < total_lanes across all operands. This could lead to out-of-bounds extract.
- **Expected Issue**: Out-of-bounds extract element or incorrect lane selection when lane index exceeds total available lanes.

### Strategy 2: ExtractLane with scalar VF and multiple parts

- **Target**: ExtractLane generation for scalar VF case
- **Rationale**: When VF.isScalar() is true, the code returns State.get(getOperand(Idx)) directly without considering the lane index across multiple parts. This assumes scalar VF means single part, but with interleaving there could be multiple scalar parts.
- **Expected Issue**: Incorrect value extraction when VF is scalar but interleaving creates multiple parts.

### Strategy 3: ExtractLane cost modeling mismatch

- **Target**: ExtractLane cost computation in computeCost
- **Rationale**: ExtractLane cost is computed as same as ExtractElement, but ExtractLane may need multiple extracts and selects across parts, which is more expensive.
- **Expected Issue**: Underestimated cost for ExtractLane leading to suboptimal vectorization decisions.

### Strategy 4: ExtractLane with FirstActiveLane returning out-of-range index

- **Target**: FirstActiveLane and ExtractLane interaction
- **Rationale**: FirstActiveLane may return index >= total_lanes if all lanes are inactive (e.g., all false). ExtractLane doesn't handle this case, assuming FirstActiveLane always returns valid index.
- **Expected Issue**: Undefined behavior when FirstActiveLane returns index equal to RuntimeVF (no active lanes).

### Strategy 5: ExtractLane unrolling with mismatched operand count

- **Target**: UnrollState::unrollBlock handling of ExtractLane
- **Rationale**: During unrolling, ExtractLane adds operands for each part, but the pattern matching expects specific operand structure. If ExtractLane has more than 2 operands initially (multiple vector sources), unrolling logic may break.
- **Expected Issue**: Crash or incorrect unrolling when ExtractLane has multiple vector operands beyond the expected pattern.

### Strategy 6: Interleaving with early exit and scalar VF in range

- **Target**: handleUncountableEarlyExit range clamping logic
- **Rationale**: The code clamps range to scalar VF when range contains both scalar and vector VFs to prevent miscompilation, but this may incorrectly disable vectorization for valid cases.
- **Expected Issue**: Unnecessary restriction preventing vectorization when both scalar and vector VFs are in range.

### Strategy 7: ExtractLane type inference for non-vector operands

- **Target**: inferScalarTypeForRecipe for ExtractLane
- **Rationale**: ExtractLane type inference assumes operand 1 is vector, but could be scalar or other type. The code returns inferScalarType(R->getOperand(1)) without validation.
- **Expected Issue**: Incorrect type inference leading to code generation failures.
