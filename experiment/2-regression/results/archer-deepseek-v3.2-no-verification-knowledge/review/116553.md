## Test Strategies

### Strategy 1: MultipleExitBlocksWithDifferentConditions

- **Target**: Loops with multiple exit blocks where header condition may not bound all exits
- **Rationale**: The fix assumes that when exiting with EQ/NE in the header, the induction value must be u<= B, as other exits may only exit earlier. However, this assumes all exits are dominated by the header condition, which may not be true if there are multiple exit blocks with different conditions.
- **Expected Issue**: Incorrectly inferring induction variable bounds in exit blocks when multiple exits exist with different conditions, potentially leading to misoptimization.

### Strategy 2: NonMonotonicInductionDueToWrapping

- **Target**: Induction variables that may wrap despite positive step
- **Rationale**: The fix assumes induction is increasing (asserts !StepOffset.isNegative()), but doesn't consider wrapping behavior. If the induction variable wraps (e.g., due to unsigned overflow), the header condition may not bound the value in exit blocks.
- **Expected Issue**: Incorrect bounds inference when induction variable wraps, leading to false optimization.

### Strategy 3: ExitBlockWithMultiplePredecessorsFromDifferentLoops

- **Target**: Exit blocks that have predecessors from multiple loops
- **Rationale**: The fix adds condition to all exit blocks from L->getExitBlocks(ExitBBs). If an exit block has predecessors from multiple loops, the added constraint may be invalid for paths coming from other loops.
- **Expected Issue**: Adding invalid constraints to shared exit blocks, causing incorrect optimization for code from other loops.

### Strategy 4: NonLoopInvariantBoundB

- **Target**: Bound B that is not actually loop-invariant despite L->isLoopInvariant(B) returning true
- **Rationale**: The code checks L->isLoopInvariant(B) but this may have false positives or the value may change in ways not captured by simple loop invariance analysis.
- **Expected Issue**: Incorrectly assuming bound is invariant when it can change, leading to invalid constraint propagation.

### Strategy 5: StepNotMultipleOfBoundMinusStart

- **Target**: Cases where (B-Start) is not a multiple of StepOffset but getConstantMultiple returns non-zero remainder
- **Rationale**: The code uses SE.getConstantMultiple(BMinusStart).urem(StepOffset).isZero() which may incorrectly return true due to conservative analysis in getConstantMultiple.
- **Expected Issue**: Assuming induction reaches bound when it may not, leading to invalid constraint that iv <= B in exit blocks.
