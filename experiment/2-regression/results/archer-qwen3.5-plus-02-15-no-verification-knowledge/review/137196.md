## Test Strategies

### Strategy 1: Test poison propagation with fcNone demanded mask

- **Target**: Return instruction with nofpclass attributes where DemandedMask becomes fcNone
- **Rationale**: When DemandedMask == fcNone, SimplifyDemandedUseFPClass returns PoisonValue. If the original return value was a valid FP value, replacing it with poison could cause UB in the caller. This tests whether the optimization incorrectly introduces poison.
- **Expected Issue**: Valid floating-point return value replaced with poison, causing potential UB when the caller uses the return value

### Strategy 2: Test multi-use instruction handling

- **Target**: Return instruction where the return value is used multiple times before the return
- **Rationale**: SimplifyDemandedUseFPClass only operates on instructions with one use (I->hasOneUse()). If the return value comes from a multi-use instruction, the optimization won't apply, but if the value is copied/aliased, there could be inconsistent simplification behavior.
- **Expected Issue**: Inconsistent simplification where some uses are simplified and others are not, leading to semantic differences

### Strategy 3: Test FastMathFlags interaction with nofpclass

- **Target**: Return instruction with FMF flags (nnan, ninf, nsz) combined with nofpclass attributes
- **Rationale**: The TODO comment at line 1926 indicates FMFs are not properly accounted for. FMFs like nnan/ninf make assumptions about the value that may conflict with or complement nofpclass attributes. Incorrect handling could lead to invalid simplifications.
- **Expected Issue**: Incorrect constant folding when FMFs and nofpclass attributes interact, potentially returning wrong constant values

### Strategy 4: Test vector type return with partial nofpclass

- **Target**: Function returning vector type with nofpclass attributes on some elements
- **Rationale**: Vector types have multiple elements, and nofpclass may apply differently to different lanes. The SimplifyDemandedUseFPClass function handles vectors, but may not correctly handle cases where only some elements match the demanded mask.
- **Expected Issue**: Incorrect simplification of vector return values where some lanes are incorrectly replaced with constants while others should remain unchanged

### Strategy 5: Test select instruction with nofpclass return

- **Target**: Return instruction where the return value is a select between two FP values with different FP classes
- **Rationale**: The SimplifyDemandedUseFPClass function has special handling for select instructions (lines 1978-1992). It checks if one side is known to never match the demanded mask. If the logic is incorrect, it could select the wrong operand or incorrectly simplify the select.
- **Expected Issue**: Select instruction incorrectly simplified to one operand when the other operand could be valid, changing program semantics

### Analysis

### Bug Triggering Analysis

The test case `test_fcfone_poison` with `nofpclass(all)` attribute triggers the edge case where all floating-point classes are excluded. When `SimplifyDemandedUseFPClass` is called with `DemandedMask = ~ReturnClass = ~all = fcNone`, the function returns `PoisonValue::get(VTy)` at line 1909 in `InstCombineSimplifyDemanded.cpp`:

```cpp
if (DemandedMask == fcNone)
  return isa<UndefValue>(V) ? nullptr : PoisonValue::get(VTy);
```

This transformation replaces the return value with poison, which is semantically correct because no valid floating-point value can satisfy `nofpclass(all)` - it's a contradiction to claim a value is simultaneously not NaN, not infinity, not zero, not subnormal, not normal, etc.

### Fix Weakness Analysis

The fix enables `SimplifyDemandedUseFPClass` for return instructions by removing the `EnableSimplifyDemandedUseFPClass` flag. The test reveals that:

1. **The optimization is working correctly**: When `nofpclass(all)` is specified, the return value is correctly replaced with poison since no valid FP value can satisfy the constraint.

2. **No bug found**: The transformation is semantically correct. Both the original IR (returning an arbitrary value with `nofpclass(all)`) and the transformed IR (returning poison) have undefined behavior - the original violates the `nofpclass(all)` contract, and the transformed explicitly returns poison.

3. **All strategies covered**: The test suite verified:
   - FastMathFlags interaction with nofpclass (no issues found)
   - Multi-use instruction handling (correctly not simplified)
   - Select instruction with nofpclass return (correctly simplified)
   - Vector type return with nofpclass (correctly simplified to poison)
   - Poison propagation with fcNone demanded mask (correctly returns poison)

The fix appears to be correct and complete. The `SimplifyDemandedUseFPClass` optimization properly handles all tested edge cases including the extreme case of `nofpclass(all)`.
