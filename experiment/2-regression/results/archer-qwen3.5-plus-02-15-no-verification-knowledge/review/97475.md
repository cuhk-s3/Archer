## Test Strategies

### Strategy 1: Poison-generating flags in select arm

- **Target**: select arm with nsw/nuw/exact flags
- **Rationale**: The fix replaces select arms with constants based on KnownBits analysis, but doesn't check if the arm contains instructions with poison-generating flags (nsw, nuw, exact, disjoint, inbounds). If such an instruction would produce poison for some inputs but the condition excludes those inputs, replacing with a constant could incorrectly propagate poison unconditionally.
- **Expected Issue**: The optimized code may produce poison for inputs where the original code would not, because the poison-generating instruction is replaced with a constant that doesn't account for the flag semantics.

### Strategy 2: Vector select with poison elements

- **Target**: vector select where condition or arms have poison elements
- **Rationale**: The hasAffectedValue function checks types but doesn't properly account for poison elements in vectors. When a vector select has some lanes with poison in the condition or arms, the KnownBits analysis might incorrectly determine that an arm can be folded to a constant, ignoring that poison lanes should remain poison.
- **Expected Issue**: Poison elements in specific vector lanes may be incorrectly replaced with constant values, changing the semantics from 'poison in those lanes' to 'defined constant in those lanes'.

### Strategy 3: i1 edge case in KnownBits computation

- **Target**: select with i1 condition and i1 arms involving boundary comparisons
- **Rationale**: The computeKnownBitsFromCmp function handles boundary conditions that could overflow for i1 types. When the condition is an icmp on i1 values, the KnownBits computation might produce incorrect results due to overflow when computing ranges (e.g., adding 1 to maximum i1 value).
- **Expected Issue**: Incorrect KnownBits inference for i1 types leading to wrong constant folding of select arms.

### Strategy 4: FCmp condition with integer select arms

- **Target**: select with floating-point comparison condition and integer arms
- **Rationale**: The findValuesAffectedByCondition has limited handling for FCmp conditions (only fneg/fabs patterns). If the select condition is an FCmp that doesn't match these patterns, the affected values might not be properly tracked, leading to incorrect KnownBits computation for the select arms.
- **Expected Issue**: Select arms are not simplified when they could be, or are incorrectly simplified because the FCmp condition's implications on integer values are not properly tracked.

### Strategy 5: Undef condition handling

- **Target**: select with undef or poison condition
- **Rationale**: The commit message mentions limiting to non-undef conditions for generalization, but the current implementation doesn't explicitly check if the condition is undef or poison. If the condition is undef, the KnownBits analysis might make invalid assumptions about which arm will be selected.
- **Expected Issue**: When the condition is undef/poison, the optimization might incorrectly fold one arm to a constant, but since undef condition means the result is undef, this could change behavior or miss opportunities to propagate undef correctly.
