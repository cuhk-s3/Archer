## Test Strategies

### Strategy 1: Vector with all undef elements matching m_AllOnes

- **Target**: PatternMatch helpers like m_AllOnes(), m_Zero(), m_SignMask()
- **Rationale**: The fix changes cstval_pred_ty to skip poison elements but not undef elements. A vector constant with ALL undef elements (no poison, no actual values) should NOT match m_AllOnes() because HasNonPoisonElements would remain false. However, before the fix, such a vector would also not match because HasNonUndefElements would be false. The key difference is: a vector with mix of -1 and undef would match before (HasNonUndefElements=true), but after the fix, a vector with mix of -1 and poison would match (HasNonPoisonElements=true). Test a vector where some lanes are -1 and some are undef vs poison to verify the matcher behavior differs correctly.
- **Expected Issue**: If the fix incorrectly handles the transition, a vector like <i32 -1, i32 undef, i32 -1> might incorrectly match m_AllOnes() when it shouldn't (since undef elements should not be ignored anymore), or the transformation might produce incorrect results when the pattern matches but the semantics differ between undef and poison.

### Strategy 2: Logical NOT pattern with vector containing undef lanes

- **Target**: simplifyOrLogic and simplifyXorInst functions using m_Not pattern
- **Rationale**: The patch removes m_NotForbidUndef and replaces it with m_Not. The original m_NotForbidUndef was designed to ensure that vector NOT operations (xor V, -1) only match when the -1 constant has no undef elements. After the fix, m_Not uses cstval_pred_ty which ignores poison but not undef. Test cases where a vector xor with a constant containing undef lanes (e.g., <i32 -1, i32 undef, i32 -1>) is used in logical simplifications like (~A ^ B) | (A & B) --> ~A ^ B. If the matcher incorrectly accepts undef-containing vectors, the simplification could be unsound.
- **Expected Issue**: Miscompilation where a logical simplification is applied incorrectly because m_Not() matches a vector constant with undef elements when it should not, leading to incorrect propagation of values through lanes that should remain undefined.

### Strategy 3: AShr of all-ones vector with poison vs undef elements

- **Target**: simplifyAShrInst function with m_AllOnes() pattern
- **Rationale**: The fix changes the comment in simplifyAShrInst from 'Do not return Op0 because it may contain undef elements' to 'We could return the original -1 constant to preserve poison elements'. The transformation '-1 >>a X --> -1' uses m_AllOnes() to match Op0. Test a vector AShr where Op0 is a vector of all -1 but with some poison elements vs some undef elements. With the fix, poison elements should be ignored by m_AllOnes(), but undef elements should cause the match to fail (or at least behave differently).
- **Expected Issue**: If m_AllOnes() incorrectly matches a vector with undef elements, the AShr simplification might return Constant::getAllOnesValue() which would have all defined -1 values, incorrectly refining undef to defined values (undef should not be refined to poison or defined values).

### Strategy 4: SignMask pattern with undef elements in vector

- **Target**: InstCombine transformation: and(shl(zext(X), Y), SignMask)
- **Rationale**: The patch removes code that sanitized undef elements in the sign mask: 'SanitizedSignMask = Constant::replaceUndefsWith(...)'. Now it just uses Op1 directly. The m_SignMask() matcher uses cstval_pred_ty which now ignores poison but not undef. Test a case where the sign mask constant has undef elements (e.g., <i32 0x80000000, i32 undef, i32 0x80000000>). The transformation should not apply or should handle undef elements correctly.
- **Expected Issue**: The transformation might incorrectly apply when the sign mask has undef elements, producing a result that incorrectly defines lanes that should remain undefined. The original code sanitized undef elements to zero, but the new code does not.

### Strategy 5: Vector with all poison elements should NOT match m_AllOnes

- **Target**: cstval_pred_ty::match() returning false for all-poison vectors
- **Rationale**: The fix requires HasNonPoisonElements to be true for a match. A vector with ALL poison elements (e.g., <i32 poison, i32 poison, i32 poison>) should NOT match m_AllOnes() because HasNonPoisonElements would remain false. This is correct behavior. However, test that this case is handled properly - the matcher should return false, not true. Compare with a vector of all undef elements which should also NOT match (HasNonPoisonElements=false since undef is not poison, but also no actual -1 values exist).
- **Expected Issue**: If the logic is inverted or incorrect, an all-poison vector might incorrectly match m_AllOnes(), leading to transformations that assume defined -1 values when actually all lanes are poison.
