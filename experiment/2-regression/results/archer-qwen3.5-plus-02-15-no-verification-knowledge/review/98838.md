## Test Strategies

### Strategy 1: Multi-use operand with external users

- **Target**: Instructions with operands that have multiple users outside the vectorization tree
- **Rationale**: The removeInstructionsAndOperands function checks if an operand hasOneUser() before marking it for deletion. However, if an operand has multiple users where some are in the tree and some are external, the operand might be incorrectly processed. The function drops all references from the dead instruction, which could affect external users if the operand is shared.
- **Expected Issue**: External users may observe incorrect values or the optimizer may incorrectly delete operands that still have live external uses, leading to use-after-free or incorrect code generation.

### Strategy 2: Operand that is a vectorized value in another tree entry

- **Target**: Operands that are VectorizedValue of other TreeEntry nodes
- **Rationale**: The code checks if an operand is a VectorizedValue of any Entry in the Entries list. However, the check only considers entries from getTreeEntry(I) and MultiNodeScalars.find(I). If an operand is a VectorizedValue of a different tree entry that is not directly related to the current instruction, it might be incorrectly marked for deletion.
- **Expected Issue**: Vectorized values from other tree entries may be incorrectly deleted, causing the generated vector code to reference deleted values.

### Strategy 3: Poison propagation in reduction with mixed signedness

- **Target**: Reduction operations where isSignedMinBitwidthRootNode() returns incorrect signedness
- **Rationale**: The new isSignedMinBitwidthRootNode() function returns the signedness from MinBWs.at(VectorizableTree.front().get()).second. If the MinBWs analysis is incorrect or if the root node's signedness doesn't match the actual requirements of the reduction, the CreateIntCast may use wrong signedness, leading to incorrect sign extension/truncation.
- **Expected Issue**: Incorrect integer cast signedness may cause sign extension errors, producing wrong results for signed reductions when unsigned was expected or vice versa.

### Strategy 4: Instruction without parent in destructor

- **Target**: Instructions in DeletedInstructions that have no parent when destructor runs
- **Rationale**: The destructor now handles instructions without a parent by inserting them before the terminator. However, if the function's entry block terminator has been modified or if the instruction's type is incompatible with the entry block, this insertion could fail or create invalid IR.
- **Expected Issue**: Compilation crash or invalid IR generation when trying to insert instructions without a parent into the entry block.

### Strategy 5: Recursive dead operand deletion with cyclic dependencies

- **Target**: Chains of instructions where operands become dead recursively
- **Rationale**: The DeadInsts processing loop recursively deletes operands that become dead. However, if there are complex dependency patterns or if an operand is used by multiple instructions being deleted simultaneously, the use_empty() check might not correctly identify all dead instructions, potentially leaving some dead code or incorrectly deleting live code.
- **Expected Issue**: Incomplete cleanup of dead instructions or premature deletion of instructions that still have live uses through complex dependency chains.
