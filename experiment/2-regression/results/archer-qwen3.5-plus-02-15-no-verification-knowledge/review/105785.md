## Test Strategies

### Strategy 1: Poison Operand Propagation

- **Target**: ucmp/scmp with poison operands
- **Rationale**: The fix does not check if operands are poison before folding ucmp/scmp to constants. If operands are poison (e.g., from division by zero, overflow with nuw/nsw flags, or out-of-bounds access), the intrinsic result should be poison, not a constant.
- **Expected Issue**: Incorrect constant folding of poison values, leading to observable behavioral changes in programs that depend on poison propagation

### Strategy 2: Vector Type Handling

- **Target**: ucmp/scmp with vector types
- **Rationale**: The fix uses ConstantInt::get(I->getType(), 1) which may not correctly handle vector types. For vector comparisons, each element should be compared independently, and the result should be a vector constant with all elements set to the same value.
- **Expected Issue**: Incorrect constant creation for vector types, potentially causing type mismatches or incorrect per-element comparison results

### Strategy 3: Signed/Unsigned Constraint System Mismatch

- **Target**: scmp with unsigned constraints or ucmp with signed constraints
- **Rationale**: The constraint system maintains separate signed and unsigned constraint systems. The fix uses getGTPredicate()/getLTPredicate() which return signed predicates for scmp and unsigned for ucmp. However, if constraints are established in the wrong system, incorrect folding may occur.
- **Expected Issue**: Incorrect folding when signedness of constraints doesn't match the intrinsic's signedness, especially with values that have different signed/unsigned interpretations (e.g., negative signed values that are large unsigned values)

### Strategy 4: Select Instruction Poison Sensitivity

- **Target**: ucmp/scmp used in select condition with potentially poison operands
- **Rationale**: Similar to the existing TODO comment at line 1506-1508 about not simplifying select conditions due to poison concerns. If ucmp/scmp is used in a select and its operands could be poison, folding it to a constant changes the select's poison behavior.
- **Expected Issue**: Select instruction that should produce poison instead produces a defined value, changing program semantics

### Strategy 5: Minimal Return Type Edge Case

- **Target**: ucmp/scmp with i2 return type
- **Rationale**: The LLVM spec states the return type must be at least i2. Testing with exactly i2 ensures the constant creation (ConstantInt::get(I->getType(), 1/-1/0)) works correctly for the minimum valid type.
- **Expected Issue**: Potential issues with constant creation for i2 type, especially for -1 which requires proper signed interpretation in a 2-bit type

### Bug #2

**Analysis:**
This is a real bug. The constraint system uses unsigned comparison (ugt) to establish that x > y, but then the optimization tries to fold a signed comparison intrinsic (scmp). The issue is that the constraint system maintains separate signed and unsigned systems, but when checking conditions for scmp, it uses getGTPredicate() which returns ICMP_SGT for scmp. However, the constraint was established in the unsigned system. The optimization incorrectly concludes that since x ugt y, then x sgt y must also hold (which is false in general, though true for positive values like 1 and 0). The actual bug is that the optimization folds scmp to 0 (equal) when it should return 1 (greater). This happens because the constraint system cannot properly reason about the signed comparison using unsigned constraints, leading to an incorrect conclusion.
