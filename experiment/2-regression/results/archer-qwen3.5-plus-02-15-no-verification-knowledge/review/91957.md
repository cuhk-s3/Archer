## Test Strategies

### Strategy 1: Test integer mul with nuw/nsw flags

- **Target**: Create integer multiplication expressions with nuw and/or nsw flags that get reassociated
- **Rationale**: The patch creates new integer multiplications using Builder.CreateMul() without preserving the nuw/nsw flags from the original instructions. This could lose important overflow semantics.
- **Expected Issue**: The hoisted multiplication may lack nuw/nsw flags that were present in the original, potentially changing overflow behavior or missing optimization opportunities

### Strategy 2: Test mixed nuw/nsw flag patterns in reassociation chain

- **Target**: Create expressions where some multiplications have nuw/nsw flags and others don't
- **Rationale**: When reassociating ((A1 * B1) + (A2 * B2)) * C, if A1*B1 has nuw but A2*B2 doesn't, the transformation needs to correctly handle flag propagation
- **Expected Issue**: Incorrect flag propagation could lead to either overly conservative code (missing optimizations) or incorrect overflow semantics

### Strategy 3: Test integer vector types with reassociation

- **Target**: Create vector integer multiplication/addition patterns that can be reassociated
- **Rationale**: The code checks isIntOrIntVectorTy() but the test file only covers scalar integers. Vector types may have different flag semantics
- **Expected Issue**: Vector integer reassociation may not correctly handle element-wise overflow flags

### Strategy 4: Test boundary case with IntAssociationUpperLimit

- **Target**: Create expressions that hit exactly the IntAssociationUpperLimit boundary
- **Rationale**: The limit check at line 2732 uses Changes.size() > Limit. Need to verify the boundary behavior is correct for integers vs floating-point
- **Expected Issue**: Off-by-one errors in limit checking could cause either missed optimizations or excessive transformations

### Strategy 5: Test reassociation with add having nuw/nsw flags

- **Target**: Create patterns where the add operations in the reassociation chain have nuw/nsw flags
- **Rationale**: The isReassociableOp function accepts any integer add, but the transformation doesn't consider add overflow flags when creating new multiplications
- **Expected Issue**: Overflow semantics from add operations may not be properly preserved through the reassociation

### Analysis

### Bug Triggering Analysis

The bug is triggered when the LICM pass performs integer multiplication reassociation on expressions with `nuw` (no unsigned wrap) flags. The transformation hoists invariant multiplications out of the loop but fails to preserve the `nuw` flag on the hoisted instructions.

**Test case explanation:**
- Original: `%mul.1 = mul nuw i64 %cell.1, %d1` and `%reass.mul = mul nuw i64 %reass.add, %delta`
- After transformation: `%factor.op.mul = mul i64 %d1, %delta` (NO nuw flag!)

With inputs `d1=2^62, delta=2`, the hoisted multiplication `d1 * delta = 2^63` overflows i64. In the original code, the final `mul nuw` would check for overflow at that point. But in the transformed code, the intermediate hoisted multiplication `factor.op.mul` doesn't have `nuw`, so it produces a wrapped value. Then when this wrapped value is used in `mul nuw i64 %cell.1, %factor.op.mul`, the nuw check on THIS multiplication may fail (if cell.1 * factor overflows), producing poison.

The difftest confirmed: original returns normally (return_code 0), transformed triggers UB (return_code 1 with "Return a poison value").

### Fix Weakness Analysis

The fix in commit 2dd52046816ac706a25d588efac77705793d8778 added integer support to `hoistMulAddAssociation` but used `Builder.CreateMul(U->get(), Factor, "factor.op.mul")` without preserving the overflow flags from the original instruction.

The code at line 2746-2747:
```cpp
if (I.getType()->isIntOrIntVectorTy())
  Mul = Builder.CreateMul(U->get(), Factor, "factor.op.mul");
```

This creates a plain `mul` without `nuw`/`nsw` flags. The fix should either:
1. Not perform this transformation for integer types with overflow flags, OR
2. Preserve the overflow flags from the original instruction when creating the hoisted multiplication

The floating-point path correctly uses `CreateFMulFMF` which preserves fast-math flags, but the integer path doesn't have equivalent flag preservation.
