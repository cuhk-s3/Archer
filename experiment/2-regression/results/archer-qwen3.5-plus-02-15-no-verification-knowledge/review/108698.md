## Test Strategies

### Strategy 1: LShr with non-constant shift amount exceeding small type width

- **Target**: lshr(zext(<N x i8>), <N x i32>) where shift amount can exceed 8
- **Rationale**: The shrinkType transformation truncates the shift amount operand. If the shift amount can be >= 8 (the small type width) but < 32 (the large type width), truncating it to i8 would change the semantics. For example, a shift amount of 256 would become 0 after trunc, changing lshr(x, 256) which is poison to lshr(x, 0) which is x.
- **Expected Issue**: The transformation incorrectly changes poison-producing shifts to valid shifts, or changes the shift amount, resulting in incorrect computation.

### Strategy 2: LShr with zext as second operand (non-commutative)

- **Target**: lshr(<N x i32>, zext(<N x i8>)) pattern
- **Rationale**: m_LShr is not commutable, so it only matches lshr(zext(x), y) where zext is the first operand. However, the code at line 2510 tries to handle both cases by checking which operand is the ZExt. If the pattern lshr(y, zext(x)) is matched (which shouldn't happen with m_LShr), the operand swapping logic could incorrectly treat the zext value as the shift amount.
- **Expected Issue**: If somehow a lshr with zext as second operand is processed, the transformation would incorrectly truncate the value being shifted instead of the shift amount, or vice versa.

### Strategy 3: Multiple users of ZExt with different opcodes

- **Target**: zext value used by both bitwise logic and non-binary operations
- **Rationale**: The code at line 2543-2544 returns false if any user of the ZExt operand is not a binary op. However, this check happens after the cost calculation has already started. If the ZExt has users that are not binary ops, the function returns false, but the iteration might have already processed some users. More importantly, if one user is a binary op that is NOT in the allowed set (bitwise logic or lshr), the transformation might still proceed incorrectly.
- **Expected Issue**: The transformation might be applied when the ZExt has users that cannot safely have the ZExt propagated through them, leading to incorrect type changes.

### Strategy 4: KnownBits analysis insufficient for shift operations

- **Target**: lshr where result KnownBits pass but shift amount has high bits
- **Rationale**: The KnownBits check at line 2518-2520 checks the result of the lshr instruction, not the shift amount operand. For lshr(zext(x), shift_amt), the result might have few active bits (e.g., if x is known to be small), but the shift_amt could have high bits set. Truncating shift_amt could change whether the shift produces poison.
- **Expected Issue**: The transformation proceeds even though truncating the shift amount would change the poison semantics of the lshr operation.

### Strategy 5: AShr not handled but similar pattern could match

- **Target**: ashr(zext(x), y) pattern
- **Rationale**: The shrinkType function only handles bitwise logic ops and lshr. It does not handle ashr (arithmetic shift right). However, if someone tries to extend the pattern to include ashr, the same issues with shift amount truncation would apply. Additionally, ashr has different semantics than lshr for negative values, and truncating the value being shifted could change the sign extension behavior.
- **Expected Issue**: If the pattern is extended to ashr without proper checks, truncating the value could change sign extension semantics, or truncating the shift amount could cause poison issues.
