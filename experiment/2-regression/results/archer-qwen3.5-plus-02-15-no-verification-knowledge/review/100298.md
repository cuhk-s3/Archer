## Test Strategies

### Strategy 1: Test floating-point condition bug

- **Target**: findValuesAffectedByCondition in ValueTracking.cpp
- **Rationale**: Line 9675 uses 'match(Cond, m_FCmp(...))' instead of 'match(V, m_FCmp(...))'. This means FCmp conditions are never properly processed in the worklist loop, only the original Cond is checked. A test with a select whose condition is an FCmp (or derived from one) would expose this bug.
- **Expected Issue**: The optimization fails to recognize affected values from floating-point comparisons, missing optimization opportunities or causing incorrect KnownBits computation.

### Strategy 2: Test poison propagation in select arm

- **Target**: Select with poison-generating operations in arms
- **Rationale**: The patch simplifies select arms to constants based on KnownBits from the condition, but doesn't verify that the original arm wouldn't produce poison. If the arm contains operations that could produce poison (like division, shifts with variable amounts, etc.), replacing them with constants changes semantics.
- **Expected Issue**: Poison that would have been produced in the original select arm is replaced with a valid constant, changing program semantics from undefined to defined behavior.

### Strategy 3: Test hasAffectedValue depth=0 edge case

- **Target**: hasAffectedValue function in InstCombineSelect.cpp
- **Rationale**: The function returns true when 'Depth != 0 && Affected.contains(V)', but at Depth=0 it continues checking operands even if V is in AffectedValues. This could cause incorrect determination of whether a value is affected, potentially leading to wrong KnownBits computation.
- **Expected Issue**: Incorrect determination of affected values leads to either missed optimizations or incorrect constant folding.

### Strategy 4: Test vector select with mixed element types

- **Target**: Vector select operations
- **Rationale**: The code checks SelType->isIntOrIntVectorTy() but the recursive hasAffectedValue check filters operands by isIntOrIntVectorTy(). For vectors where some operations involve non-integer intermediate types, this could miss affected values or incorrectly compute KnownBits per element.
- **Expected Issue**: Vector select with element-wise conditions produces incorrect results when intermediate values have non-integer types.

### Strategy 5: Test condition with logical operators affecting KnownBits

- **Target**: Select with complex logical conditions (and/or/not)
- **Rationale**: The computeKnownBitsFromCond function handles logical operators, but the interaction with the injected CondContext and the Invert flag may not correctly handle all combinations. Testing with conditions like '(A && B)' or '(A || B)' where the select arm uses values affected by both A and B could expose issues.
- **Expected Issue**: KnownBits computation is incorrect for select arms when the condition involves logical combinations, leading to wrong constant folding.

### Analysis

### Bug Triggering Analysis

The test case `vec_select_no_equivalence` triggers a bug in the InstCombine optimization pass. When given:
- Input: `%x = <0, 2>`
- The shuffle creates `%x10 = <2, 0>` (swapping elements)
- The condition `%cond = icmp eq %x, <0, 0>` evaluates to `<true, false>`
- The select should produce: `<x10[0], x[1]> = <2, 2>`

However, the optimization incorrectly transforms the entire select to just return `%x`, producing `<0, 2>` instead of `<2, 2>`.

This is a miscompilation bug where the optimization incorrectly assumes that when the condition is element-wise comparison with zero, and one arm is a shuffle of the input, the result can be simplified to just the input. This is incorrect because the shuffle changes which elements are selected.

### Fix Weakness Analysis

The fix introduced in commit 77eb05683082dd3751ccfab963f5160f1852058d adds logic to simplify select arms based on KnownBits implied by the condition. However, the implementation has a weakness:

1. The `hasAffectedValue` function may incorrectly determine which values are affected by the condition, especially for vector operations with shuffle instructions.

2. The optimization doesn't properly handle the case where the select arm is a shuffle of the input that depends on the condition in a non-trivial way. When the condition is element-wise, each element of the result may come from different sources, and the optimization incorrectly collapses this to a simpler form.

3. The KnownBits analysis for vector types may not correctly track per-element knowledge, leading to over-aggressive simplification.

The bug is exposed because the test uses a vector select with element-wise condition where:
- Element 0: condition is true, so result should be x10[0] = 2
- Element 1: condition is false, so result should be x[1] = 2

But the optimization incorrectly simplifies this to just return x = <0, 2>, which is wrong for element 0.
