## Test Strategies

### Strategy 1: Test with all shift types (shl, lshr, ashr)

- **Target**: Modify existing test to use different shift operations as the single user of ctlz/cttz
- **Rationale**: The fix uses m_Shift which matches shl, lshr, and ashr. We need to verify the optimization applies correctly to all three shift types and produces equivalent poison behavior.
- **Expected Issue**: If the fix incorrectly handles any shift type, the optimization might not apply or might produce incorrect results for that specific shift type.

### Strategy 2: Test with shift flags (exact, nuw, nsw)

- **Target**: Add shift flags to the shift instruction that uses ctlz/cttz result
- **Rationale**: The fix doesn't check if the shift has flags like exact, nuw, or nsw. These flags add additional poison conditions that might interact unexpectedly with the poison from ctlz/cttz(0).
- **Expected Issue**: If the shift has flags, the combination of poison from ctlz/cttz and the flag conditions might produce different observable behavior than expected.

### Strategy 3: Test with vector types having mixed zero/non-zero elements

- **Target**: Create a vector test where some lanes have zero input to ctlz/cttz and others have non-zero
- **Rationale**: For vectors, the fix should handle each lane independently. If some lanes have zero input (producing poison) and others don't, we need to verify the poison propagates correctly only for the affected lanes.
- **Expected Issue**: If the fix doesn't correctly handle vector semantics, poison might propagate to all lanes instead of just the lanes with zero input.

### Strategy 4: Test with multiple uses of ctlz/cttz

- **Target**: Create a test where ctlz/cttz has multiple uses, with only one being a shift
- **Rationale**: The fix requires hasOneUse(). If there are multiple uses, the optimization should not apply. We need to verify this condition is correctly enforced.
- **Expected Issue**: If the hasOneUse() check is bypassed or incorrect, the optimization might apply when it shouldn't, changing semantics for other users.

### Strategy 5: Test with is_zero_poison already true

- **Target**: Create a test where ctlz/cttz already has is_zero_poison=true
- **Rationale**: The fix checks match(Op1, m_Zero()) to ensure is_zero_poison is currently false. If it's already true, the optimization should not apply (nothing to change).
- **Expected Issue**: If the m_Zero() check fails to correctly identify is_zero_poison=true, the optimization might incorrectly try to change an already-true flag.

### Analysis

### Summary of Fix Analysis

The patch adds an optimization in InstCombine that sets `is_zero_poison` to `true` for `ctlz/cttz` intrinsics when:
1. The intrinsic has exactly one use (`II.hasOneUse()`)
2. The current `is_zero_poison` flag is `false` (`match(Op1, m_Zero())`)
3. The single user is a shift instruction where the ctlz/cttz result is used as the shift amount

**Semantic Correctness:**
- When input is 0: `cttz(0, false)` returns bit_width (e.g., 32 for i32), and `shift(v, 32)` produces poison (shift amount >= bit width). With `is_zero_poison=true`, `cttz(0, true)` returns poison, and `shift(v, poison)` also produces poison. Both paths produce poison, so the transformation is semantically equivalent.
- When input is non-zero: `cttz(x, false)` and `cttz(x, true)` both return the same count value (in range [0, bit_width-1]), so the shift behavior is identical.
