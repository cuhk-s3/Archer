## Test Strategies

### Strategy 1: Vector constant with mixed signs

- **Target**: computeKnownFPClass vector constant handling
- **Rationale**: The patch adds sign bit tracking for vector constants. The logic checks if SignBitAllOne != SignBitAllZero before setting SignBit. However, if the vector contains a mix of positive and negative values, both SignBitAllZero and SignBitAllOne would be false, and SignBit would remain unset (std::nullopt). But if the vector contains only NaN values (which have no meaningful sign), the logic might incorrectly set SignBit. Test with vectors containing all NaNs, or vectors with a mix of NaNs and signed values.
- **Expected Issue**: Incorrect sign bit inference for vector constants containing NaN elements or mixed signed/NaN elements, leading to incorrect copysign/fabs optimizations

### Strategy 2: Min/max with NaN operands

- **Target**: minnum/maxnum/minimum/maximum sign bit inference
- **Rationale**: The patch adds sign bit inference for min/max intrinsics at line 4598-4617, but this is guarded by `Known.isKnownNeverNaN()`. However, the condition at line 4598 checks if the RESULT is never NaN, not the operands. For minnum/maxnum, the result can be non-NaN even if one operand is NaN (it returns the non-NaN operand). The sign bit inference logic at lines 4610-4615 uses KnownLHS.SignBit and KnownRHS.SignBit which could be std::nullopt if one operand is NaN, but the condition doesn't properly handle this case.
- **Expected Issue**: Incorrect sign bit inference for minnum/maxnum when one operand is known NaN and the other has known sign, potentially causing incorrect copysign simplification

### Strategy 3: FMul sign bit with NaN operands

- **Target**: FMul sign bit inference at lines 4967-4972
- **Rationale**: The patch adds sign bit inference for FMul when both operands have known sign bits (line 4967-4972). However, this logic is executed after checking that neither operand is NaN (lines 4959-4965). But the sign bit inference doesn't account for the case where the result could be NaN due to 0*inf. The code at lines 4974-4978 handles this, but the sign bit was already set before this check. If 0*inf produces NaN, the sign bit of NaN is undefined, but the code may have already set it.
- **Expected Issue**: Sign bit incorrectly set for FMul result that becomes NaN due to 0*inf, leading to incorrect downstream optimizations

### Strategy 4: Copysign with negative sign argument

- **Target**: InstCombine copysign optimization
- **Rationale**: The patch changes the copysign optimization to use computeKnownFPSignBit which returns std::optional<bool>. When the sign bit is known to be 1 (negative), it transforms copysign(Mag, -Sign) to fneg(fabs(Mag)). However, the old code only checked for constant negative values. The new code might trigger for non-constant values where the sign bit is inferred. The issue is that fneg(fabs(x)) always produces a negative result (or -0), but copysign(x, negative) should preserve the magnitude's special values like NaN payload. If Mag is NaN, copysign(NaN, -Sign) should preserve NaN, but fneg(fabs(NaN)) might not preserve the NaN payload correctly.
- **Expected Issue**: Incorrect transformation of copysign when magnitude is NaN, potentially losing NaN payload or changing signaling/quiet NaN type

### Strategy 5: knownNot sign bit inference with NaN

- **Target**: KnownFPClass::knownNot() method
- **Rationale**: The patch adds logic in knownNot() (lines 361-366) to infer sign bit when NaN is ruled out. The condition `isKnownNever(fcNan) && !SignBit` checks if NaN is ruled out and SignBit is not yet set. Then it checks if fcNegative or fcPositive is ruled out to set SignBit. However, this logic assumes that if NaN is ruled out and fcNegative is ruled out, then SignBit must be false (positive). But this doesn't account for the case where the value could be zero - zeros have a sign bit but are neither positive nor negative in the FPClassTest sense (fcPositive doesn't include fcPosZero, fcNegative doesn't include fcNegZero).
- **Expected Issue**: Incorrect sign bit inference when value is known to be non-NaN and non-negative but could be +0 or -0, leading to incorrect sign bit determination

### Analysis

### Summary of Fix Analysis

The patch merges `cannotBeOrderedLessThanZeroImpl` into `computeKnownFPClass` to improve sign bit inference for floating-point values. Key changes include:

1. **New `knownNot()` logic**: Infers sign bit when NaN is ruled out and either fcNegative or fcPositive is ruled out.

2. **New `signBitMustBeOne()` method**: Sets SignBit to true and restricts KnownFPClasses to negative or NaN.

3. **Vector constant handling**: Properly tracks sign bit for vector constants.

4. **Min/max sign inference**: Added logic to infer sign bit for minnum/maxnum/minimum/maximum results.

5. **FMul sign inference**: Added sign bit inference when multiplying two values with known sign bits.

6. **API change**: `SignBitMustBeZero()` was replaced with `computeKnownFPSignBit()` returning `std::optional<bool>`.

### Testing Results

After extensive testing with the provided test cases and additional mutations:
- All transformations verified correctly by alive2 (except for unknown libcall approximations for powi)
- Differential testing showed no execution differences between original and optimized code
- The fix successfully enables more aggressive optimizations for copysign, fabs, powi, and other floating-point operations

### Potential Issues Identified (but not triggered)

1. **NaN payload preservation**: The copysign transformation `copysign(NaN, -Sign) → fneg(fabs(NaN))` may not preserve NaN payloads correctly, but this is a subtle semantic issue that doesn't affect correctness for most use cases.

2. **Vector constants with mixed NaN/sign values**: The sign bit tracking for vectors with mixed NaN and signed elements could potentially have edge cases, but testing showed correct behavior.

3. **FMul 0*inf sign bit**: The sign bit is set before checking for 0*inf NaN, but the subsequent NaN check clears the sign bit appropriately.

No actual bugs were found during testing. The fix is correct and improves sign bit inference precision.
