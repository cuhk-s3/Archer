## Test Strategies

### Strategy 1: Chain of GEPs with mixed nowrap flags

- **Target**: Create a chain of 2+ GEPs where intermediate GEPs have different nowrap flags (e.g., first GEP has nuw, second has nusw, neither has inbounds)
- **Rationale**: The CommonPointerBase::compute uses simple & intersection for flags. The intersectForOffsetAdd method suggests that nusw preservation requires additional conditions. Testing mixed flags could expose incorrect flag propagation.
- **Expected Issue**: The optimization might incorrectly preserve nusw/nuw flags when combining offsets from GEPs with different flag combinations, leading to poison propagation or missed optimization opportunities.

### Strategy 2: GEP chain with vector pointer types

- **Target**: Create a chain of GEPs operating on vector pointer types (<N x ptr>) comparing against a base vector pointer
- **Rationale**: The EmitGEPOffsets handles vector splatting, but CommonPointerBase::compute doesn't explicitly handle vector pointer type comparisons. The type equality check might fail for vectors.
- **Expected Issue**: The optimization might not trigger for vector pointer GEP chains, or might incorrectly handle the vector element count during offset computation.

### Strategy 3: GEP chain through address space casts

- **Target**: Create a chain where GEPs are separated by addrspacecast instructions between different sized address spaces
- **Rationale**: CommonPointerBase::compute only follows GEP operands directly. If there are addrspacecasts between GEPs in the chain, they won't be traversed, potentially missing valid optimization opportunities or causing type mismatches.
- **Expected Issue**: The optimization might fail to recognize common bases when address space casts are interleaved with GEPs, or might produce incorrect offset types.

### Strategy 4: GEP chain where offset addition would overflow

- **Target**: Create a GEP chain where individual GEPs have nusw flags but the combined offset would overflow (e.g., large positive offset followed by large negative offset in the chain)
- **Rationale**: The intersectForOffsetAdd method specifically handles the case where nusw can only be preserved if x+y doesn't wrap. Simple & intersection might incorrectly preserve nusw when the combined offset could overflow.
- **Expected Issue**: The optimization might incorrectly apply nusw flags to the combined offset comparison, causing valid programs to produce poison when the individual GEP offsets don't overflow but their sum does.

### Strategy 5: GEP chain with inbounds on inner but not outer GEP

- **Target**: Create a chain where the inner GEP (closer to base) has inbounds but the outer GEP doesn't, then compare with base
- **Rationale**: Since inbounds implies nusw, but the outer GEP without inbounds might not have nusw, the intersection logic needs to correctly handle this case. The semantics of comparing a partially-inbounds chain with the base needs verification.
- **Expected Issue**: The optimization might incorrectly fold the comparison when only part of the GEP chain is inbounds, potentially changing the poison semantics of the comparison result.

### Analysis

### Bug Triggering Analysis

The bug is triggered when folding a comparison between a chain of GEPs with nusw (no unsigned signed wrap) flags and the base pointer, where the combined offset would overflow even though individual GEP offsets might not.

In the test case:
- `%g1 = getelementptr nusw i8, ptr %p, i64 %x` - GEP with nusw flag
- `%g2 = getelementptr nusw i8, ptr %g1, i64 %y` - Another GEP with nusw flag
- `%cmp = icmp eq ptr %g2, %p` - Compare result with base

When x = 9223372036854775807 (i64 max) and y = 1:
- The first GEP with offset x causes signed overflow because adding x to the base pointer wraps around
- This makes %g1 poison, which propagates to %g2 and then to the comparison result
- The original code returns poison (UB)

However, the optimized code transforms this to:
- `%cmp = icmp eq i64 %x, -%y` which is `icmp eq i64 9223372036854775807, -1` = false
- This returns a concrete value (false) instead of poison

This is a refinement failure - the optimized code is more defined than the original, violating LLVM's semantics.

### Fix Weakness Analysis

The weakness is in `CommonPointerBase::compute()` in InstCombineAddSub.cpp. It uses simple bitwise AND (`&`) to intersect nowrap flags across the GEP chain:

```cpp
Base.LHSNW &= GEP->getNoWrapFlags();
```

However, the `GEPNoWrapFlags::intersectForOffsetAdd()` method in GEPNoWrapFlags.h specifically notes that nusw can only be preserved if the sum of offsets doesn't wrap:

```cpp
/// Given (gep (gep p, x), y), determine the nowrap flags for (gep p, x+y).
GEPNoWrapFlags intersectForOffsetAdd(GEPNoWrapFlags Other) const {
  GEPNoWrapFlags Res = *this & Other;
  // Without inbounds, we could only preserve nusw if we know that x + y does
  // not wrap.
  if (!Res.isInBounds() && Res.hasNoUnsignedSignedWrap())
    Res = Res.withoutNoUnsignedSignedWrap();
  return Res;
}
```

The fix incorrectly applies simple `&` intersection without checking whether the combined offset could overflow. When folding `(gep (gep p, x), y) cmp p` to `(x + y) cmp 0`, the nusw flag should only be preserved if we can prove that x + y doesn't overflow. The current implementation blindly preserves nusw through the `&` operation, leading to incorrect poison semantics.

The fix should either:
1. Drop nusw flags when combining offsets from multiple GEPs (unless inbounds is present)
2. Add a check to verify that the combined offset cannot overflow before preserving nusw
