## Test Strategies

### Strategy 1: Test both predicates with samesign

- **Target**: isImpliedCondCommonOperandWithCR with both LPred and RPred having samesign flag
- **Rationale**: The fix only handles the case when exactly one predicate has samesign (XOR condition). When both predicates have samesign, the function returns std::nullopt without attempting the signedness flip. This could miss valid implications where both icmps have samesign and the signedness flip would reveal an implication.
- **Expected Issue**: Missed optimization opportunity where 'icmp samesign ugt X, C1' should imply 'icmp samesign uge X, C2' but the analysis returns std::nullopt

### Strategy 2: Test samesign with mixed-sign constant ranges

- **Target**: isImpliedCondCommonOperandWithCR where the constant range includes both positive and negative values
- **Rationale**: The samesign flag means the result is poison if operands have different signs. When the constant range includes both positive and negative values, flipping signedness may not be valid because the samesign icmp could produce poison for some values in the range while the flipped predicate would produce valid results. The fix doesn't check if the constant range is all-nonnegative or all-negative before flipping.
- **Expected Issue**: Incorrect implication where 'icmp samesign ult X, [negative, positive]' is treated as implying something about 'icmp slt X, [negative, positive]' even though samesign ult produces poison for mixed-sign values

### Strategy 3: Test samesign ult implying slt with negative constant

- **Target**: Case where samesign ult with a negative constant should NOT imply slt
- **Rationale**: Consider 'icmp samesign ult i32 X, -1'. Since -1 is negative, for this to not be poison, X must also be negative. But samesign ult with negative operands doesn't have the same semantics as slt. The fix flips samesign ult to slt, but this transformation is only valid when we know operands have the same sign AND are in a range where ult and slt are equivalent.
- **Expected Issue**: Wrong implication: 'icmp samesign ult X, -1' might be incorrectly treated as implying 'icmp slt X, -1' when X could be positive (making samesign ult produce poison while slt produces false)

### Strategy 4: Test computeConstantRange signedness parameter with samesign

- **Target**: The computeConstantRange call at line 9463 uses ICmpInst::isSigned(LPred) which doesn't account for samesign
- **Rationale**: When computing the constant range for a samesign predicate, the ForSigned parameter should consider whether the samesign predicate should be treated as signed or unsigned. Currently, isSigned() only checks the base predicate (e.g., ult is unsigned), ignoring the samesign flag. This could lead to incorrect constant range computation for samesign predicates.
- **Expected Issue**: Incorrect constant range computed for 'icmp samesign ult' - treated as unsigned range when it should potentially be treated as signed range due to samesign semantics

### Strategy 5: Test samesign with equality predicates

- **Target**: Cases involving samesign with EQ/NE predicates
- **Rationale**: The fix uses getFlippedSignednessPredicate which returns the same predicate for EQ/NE (line 3845-3846 in Instructions.cpp). If one predicate is samesign eq and the other is regular eq, the XOR condition triggers but flipping signedness does nothing for EQ. This could lead to incorrect or missed implications.
- **Expected Issue**: Edge case where 'icmp samesign eq X, C' and 'icmp eq X, C' are compared - the fix attempts to flip but EQ stays EQ, potentially causing incorrect analysis

### Analysis

### Bug Triggering Analysis

The bug is triggered when the optimizer incorrectly assumes that `icmp samesign ult X, -1` implies `icmp slt X, -1`.

**Test case:** `test_samesign_ult_implies_slt` with input x=0

**Original behavior:**
- `%cmp1 = icmp samesign ult i32 0, -1`: Since 0 is positive and -1 (0xFFFFFFFF) is negative, the samesign flag triggers and produces **poison**
- `%cmp2 = icmp slt i32 0, -1`: This evaluates to **false** (0 is not less than -1 in signed comparison)
- `%and = and i1 poison, false`: This produces **poison** (and with poison propagates poison)
- `ret i1 poison`: This is **immediate UB** (returning poison)

**Transformed behavior:**
- The optimizer simplified `(samesign ult && slt)` to just `slt`
- Returns `slt(0, -1) = false` (a valid value, no UB)

**Why this is a bug:** The transformation changes the program's semantics. The original has UB (return poison) while the transformed version returns a valid value (false). This is an incorrect optimization because the implication `samesign ult X, -1 => slt X, -1` is not valid when X can have a different sign than -1.

### Fix Weakness Analysis

The fix in `isImpliedCondCommonOperandWithCR` attempts to handle samesign by flipping signedness when exactly one predicate has the samesign flag (XOR condition). However, the fix has a critical weakness:

1. **Missing poison check:** The fix doesn't verify that the constant range is compatible with the samesign semantics. When flipping `samesign ult` to `slt`, it assumes the implication holds, but this is only true when both operands have the same sign. If the constant range includes values with different signs, the samesign predicate produces poison while the flipped predicate produces valid results.

2. **Incorrect implication inference:** The fix treats `samesign ult X, C` as implying `slt X, C` (after signedness flip) without checking if X and C can have different signs. In the test case, `samesign ult 0, -1` produces poison (different signs), but `slt 0, -1` produces false (valid). The optimizer incorrectly uses this "implication" to simplify the code.

3. **No validation of constant range sign consistency:** The `computeConstantRange` function is called with `ICmpInst::isSigned(LPred)` which returns false for `ult` even with samesign. This means the constant range is computed as unsigned, potentially missing the sign constraints that samesign imposes.

The fix should either:
- Check that the constant range is all-nonnegative or all-negative before applying the signedness flip
- Or not apply the implication when the samesign predicate could produce poison
