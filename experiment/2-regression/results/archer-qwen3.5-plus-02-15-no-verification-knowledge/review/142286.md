## Test Strategies

### Strategy 1: Non-contiguous case values with small range

- **Target**: switch.ll - test_unreachable_default
- **Rationale**: The fix checks if CR.isSizeLargerThan(ReachableCaseCount) is false, meaning range size <= case count. However, this doesn't guarantee all values in the range are covered by cases. If cases are non-contiguous (e.g., cases 0, 2, 4) and the range is [0,3) with size 3, the condition passes but value 1 in the range is not covered by any case, making default reachable.
- **Expected Issue**: CVP incorrectly marks default as unreachable when it's actually reachable for values in the range not covered by non-contiguous cases, leading to miscompilation where valid execution paths are replaced with unreachable.

### Strategy 2: Single reachable case with matching range

- **Target**: switch.ll - test_unreachable_default
- **Rationale**: The fix has condition 'ReachableCaseCount > 1', requiring at least 2 reachable cases. If there's exactly 1 reachable case and the range size is 1 (single value), the default should be unreachable but the fix won't trigger. This is a missed optimization opportunity that could indicate incomplete logic.
- **Expected Issue**: CVP fails to mark default as unreachable when there's exactly 1 reachable case that covers the entire range, missing a valid optimization.

### Strategy 3: Range with wrap-around semantics

- **Target**: switch.ll - test_unreachable_default
- **Rationale**: ConstantRange can represent wrap-around sets where Lower > Upper. The isSizeLargerThan function handles full sets specially but the size calculation (Upper - Lower) for wrapped ranges may not correctly represent the number of distinct values. A wrapped range with small computed size might pass the check even when not all values are covered.
- **Expected Issue**: CVP incorrectly computes range size for wrap-around ConstantRanges, leading to incorrect determination that default is unreachable.

### Strategy 4: Undef in switch condition affecting range

- **Target**: switch.ll - test_unreachable_default_cond_may_be_undef
- **Rationale**: The fix calls getConstantRangeAtUse with UndefAllowed=false. However, if the switch condition can be undef, LVI may return an overly optimistic range. The existing test test_unreachable_default_cond_may_be_undef expects the default to remain reachable when condition may be undef, but the fix's range check might incorrectly conclude default is unreachable.
- **Expected Issue**: CVP incorrectly marks default as unreachable when switch condition can be undef, because getConstantRangeAtUse with UndefAllowed=false may return a constrained range that doesn't account for undef evaluating to uncovered values.

### Strategy 5: Range size equals case count but with gaps

- **Target**: switch.ll - new test case
- **Rationale**: Create a switch with cases at values 0, 5, 10 (3 cases) where LVI determines the range is [0, 11) but only values 0, 5, 10 are actually possible due to prior constraints. The range size (11) would be larger than case count (3), so this wouldn't trigger. Instead, test with range [0, 3) and cases 0, 1, 2 but where value 1 is actually not possible due to other constraints not captured by LVI.
- **Expected Issue**: Edge case where LVI's range analysis is imprecise - reports a range that includes values not actually possible, but the case count matches, leading to incorrect unreachable marking.

### Analysis

### Bug Triggering Analysis
The fix in CorrelatedValuePropagation's processSwitch function attempts to mark a switch's default case as unreachable when the constant range size of the switch condition is <= the number of reachable cases. However, this logic is flawed because it assumes that if range_size <= case_count, then all values in the range are covered by the cases. This is only true if the case values are contiguous and exactly match the range.

The test case `test_noncontiguous_cases` demonstrates this issue:
- The switch condition `%masked = and i8 %x, 3` produces values in range [0, 4) = {0, 1, 2, 3}
- There are only 2 cases: 0 and 2
- Range size (4) > case count (2), so the fix correctly doesn't trigger

However, the real bug would occur when:
- LVI reports a range like [0, 3) = {0, 1, 2} (size 3)
- There are 3 cases at values 0, 2, and some other value that doesn't cover 1
- The fix would incorrectly conclude default is unreachable because 3 <= 3

### Fix Weakness Analysis
The fix's weakness is that it uses a simple size comparison (`!CR.isSizeLargerThan(ReachableCaseCount)`) without verifying that the case values actually cover all values in the range. This is a fundamental flaw in the optimization logic - range size <= case count does NOT imply full coverage unless the cases are known to be contiguous.

The fix also has the `ReachableCaseCount > 1` check which excludes valid single-case scenarios where the default should be marked unreachable.

After extensive testing with all 7 test cases from tests_manager covering all 5 proposed strategies (Non-contiguous case values, Undef handling, Single reachable case, Wrap-around semantics, and Range with gaps), no actual bugs were found in the current implementation. The fix appears to be working correctly because:
1. LVI's range analysis is typically precise enough that the size check doesn't incorrectly pass
2. The `UndefAllowed=false` parameter helps prevent overly optimistic ranges
3. The existing test cases in the LLVM test suite already cover the edge cases

The fix is correct but could be more aggressive (e.g., handling the single-case scenario).
