## Test Strategies

### Strategy 1: Constant on Left Operand for Commutative Ops

- **Target**: BinaryOperator with constant on left operand (operand 0) instead of right (operand 1)
- **Rationale**: The fix only checks BO->getOperand(1) for a constant mask using m_APInt. For commutative operations (and, or, xor), the constant could be on the left side. The current code would miss these cases, failing to simplify when it should.
- **Expected Issue**: Binary operations like `or i64 3, %a` where the constant 3 is on the left side will not be simplified even when the demanded bits don't intersect with the mask, leading to missed optimization opportunities.

### Strategy 2: Vector Constants with Undef Elements

- **Target**: Vector binary operations with splat constants containing undef elements
- **Rationale**: The m_APInt matcher by default forbids undefs in splat vector constants. If the binary operation has a vector constant with undef elements that would otherwise be safe to remove, the match will fail and the optimization won't be applied.
- **Expected Issue**: Vector operations like `or <2 x i32> %a, <i32 3, i32 undef>` will not be simplified even when the demanded bits don't intersect with the defined portions of the mask.

### Strategy 3: Disjoint Or with Non-Intersecting Demanded Bits

- **Target**: Disjoint or operations where mask doesn't affect demanded bits
- **Rationale**: The fix treats 'or' and 'xor' the same way (!Demanded.intersects(*Mask)). However, 'or disjoint' has additional semantics that the inputs don't overlap. We should verify the fix handles disjoint or correctly, especially when combined with multi-use scenarios.
- **Expected Issue**: Disjoint or operations might be incorrectly simplified or not simplified when they should be, particularly in edge cases where the disjoint property interacts with demanded bits analysis.

### Strategy 4: Multi-Use Binary Op with Mixed Demanded Bits

- **Target**: Binary operation with multiple uses having different demanded bit patterns
- **Rationale**: The fix uses DB.getDemandedBits(BO) which returns the union of demanded bits from all uses. If different uses demand different non-overlapping bit ranges, the combined Demanded mask might incorrectly prevent simplification even when the mask doesn't affect any individual use.
- **Expected Issue**: A binary op used in two places - one demanding bits 0-3 and another demanding bits 8-11 - with a mask of 0xF0 (bits 4-7) might not be simplified because the union of demanded bits could be computed incorrectly or the intersection check might fail.

### Strategy 5: Xor with All-Ones Mask (Not Operation)

- **Target**: Xor operations with all-ones mask (equivalent to bitwise not)
- **Rationale**: Xor with all-ones is equivalent to 'not'. If only some bits are demanded, the fix should simplify `xor %a, -1` to just `%a` when no demanded bits intersect with the mask. However, if the mask is all-ones, Demanded.intersects(*Mask) will always be true (unless Demanded is zero), so this case might not be simplified correctly.
- **Expected Issue**: Xor operations with all-ones mask (bitwise not) where only a subset of bits are demanded might not be simplified correctly, especially when the demanded bits are a proper subset of all bits.
