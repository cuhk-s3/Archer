## Test Strategies

### Strategy 1: UDivExpr with non-dominating divisor

- **Target**: Test where SCEV contains a udiv expression where the divisor does not properly dominate the PHI block but the dividend does
- **Rationale**: The old IsAvailableOnEntry would immediately mark scUDivExpr as unavailable, while the new properlyDominates recursively checks operands. If the divisor is an instruction that doesn't properly dominate the block, the new code would return DoesNotDominateBlock, but if only the dividend dominates, there could be a discrepancy in behavior.
- **Expected Issue**: SCEV may incorrectly create a select node for a PHI when one of the operands contains a udiv whose divisor could trap, potentially leading to incorrect optimization or missed fault detection

### Strategy 2: Nested expression with mixed dominance

- **Target**: Test with nested SCEV expressions where some operands properly dominate and others only dominate (same block)
- **Rationale**: The computeBlockDisposition function distinguishes between ProperlyDominatesBlock and DominatesBlock. An instruction in the same block as the PHI returns DominatesBlock, not ProperlyDominatesBlock. The old IsAvailableOnEntry would mark such cases as unavailable via setUnavailable(), but the new code allows DominatesBlock.
- **Expected Issue**: createNodeFromSelectLikePHI may incorrectly succeed when operands are defined in the same block as the PHI, potentially creating incorrect SCEV expressions

### Strategy 3: AddRecExpr in sibling loop

- **Target**: Test where an AddRecExpr is from a sibling loop that dominates the PHI block
- **Rationale**: The old IsAvailableOnEntry only allowed AddRecExprs from the same loop or outer loops. The new computeBlockDisposition uses DT.dominates() which would allow AddRecExprs from sibling loops if they dominate. This is a semantic expansion.
- **Expected Issue**: SCEV may create select nodes for PHIs with operands from sibling loops, which could lead to incorrect loop analysis or expansion

### Strategy 4: Unknown SCEV from Argument in unreachable block

- **Target**: Test with SCEVUnknown wrapping an Argument value where the PHI is in a block not reachable from entry
- **Rationale**: The old IsAvailableOnEntry returned false for Arguments (returning false directly without setUnavailable). The new computeBlockDisposition returns ProperlyDominatesBlock for non-Instruction SCEVUnknown values. This could change behavior for arguments.
- **Expected Issue**: Incorrect SCEV creation for PHIs with argument operands in specific control flow configurations

### Strategy 5: CouldNotCompute in expression tree

- **Target**: Test where an SCEV expression tree contains a CouldNotCompute sub-expression
- **Rationale**: The old IsAvailableOnEntry would immediately mark scCouldNotCompute as unavailable. The new computeBlockDisposition has llvm_unreachable for scCouldNotCompute, which means it should never be called with such values. However, if CouldNotCompute somehow appears in the tree, the behavior differs.
- **Expected Issue**: Potential assertion failure or incorrect behavior if CouldNotCompute expressions reach the properlyDominates check

### Analysis

### Bug Triggering Analysis

The patch replaces `IsAvailableOnEntry` with `properlyDominates` for checking if SCEV expressions can be used in select-like PHI patterns. The key semantic difference is:

1. **Old behavior (IsAvailableOnEntry)**: `scUDivExpr` was always marked as unavailable, regardless of whether its operands properly dominated the block.

2. **New behavior (properlyDominates)**: `scUDivExpr` is treated like other n-ary expressions - it recursively checks if all operands properly dominate the block.

The test case `test_udiv_select_nonconst` creates a select-like PHI pattern where one operand is a `udiv` expression. The old code would never create an SCEV select node for this pattern because `scUDivExpr` was always unavailable. The new code allows it if both operands of the udiv properly dominate the PHI block.

However, after extensive testing with both `verify` (alive2) and `difftest` (llubi/lli), no actual bug was found. All test cases showed:
- Correct transformations (syntactically equal or semantically equivalent)
- No execution differences between original and optimized code
- No crashes or assertion failures

### Fix Weakness Analysis

The fix appears to be correct because:

1. **UDivExpr handling**: The new `properlyDominates` correctly checks that all operands of a udiv properly dominate the block. If the divisor could be zero, the udiv itself would cause UB, but this is independent of the SCEV analysis.

2. **AddRecExpr from sibling loops**: The new code uses `DT.dominates()` which allows AddRecExpr from any dominating loop, not just same/outer loops. This is a semantic expansion but appears correct because if the loop header dominates the PHI block, the AddRecExpr value is available.

3. **Arguments as SCEVUnknown**: The new code treats non-Instruction SCEVUnknown (including Arguments) as `ProperlyDominatesBlock`. This is correct because function arguments are available at all blocks.

4. **CouldNotCompute**: The `llvm_unreachable` for `scCouldNotCompute` is appropriate because such expressions should never reach the `properlyDominates` check in normal operation.

The fix is a refactoring that replaces a custom availability check with the more general block disposition mechanism. The semantic differences are intentional expansions that allow more SCEV expressions to be recognized in select-like PHI patterns, but the core correctness is maintained through the dominance checks.
