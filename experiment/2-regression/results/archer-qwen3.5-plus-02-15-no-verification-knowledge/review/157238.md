## Test Strategies

### Strategy 1: Test non-IEEE float types

- **Target**: Bitcast from integer to non-IEEE float types (x86_fp80, ppc_fp128, bfloat)
- **Rationale**: The fix only handles Ty->isIEEE() floats. Non-IEEE float types like x86_fp80, ppc_fp128, and bfloat are not covered. Testing bitcasts to these types could reveal missing analysis or incorrect assumptions.
- **Expected Issue**: The fpclass analysis may not infer any information for non-IEEE float bitcasts, or may incorrectly apply IEEE-specific logic.

### Strategy 2: Test signed infinity detection

- **Target**: Bitcast where sign bit is known and value equals +Inf or -Inf specifically
- **Rationale**: The code clears the sign bit in InfKB.Zero, making it sign-agnostic. But the equality check Bits == InfKB requires exact match. If sign bit is known to be 0 (positive), it won't match the sign-agnostic InfKB, missing the opportunity to infer fcPosInf.
- **Expected Issue**: When the integer's sign bit is known to be 0 and the rest matches +Inf, the analysis may not infer fcPosInf because the equality check fails against the sign-agnostic InfKB.

### Strategy 3: Test signed zero detection

- **Target**: Bitcast where sign bit is known and value equals +0 or -0 specifically
- **Rationale**: Similar to infinity, ZeroKB has sign bit cleared. If the sign bit is known, the equality check may fail, missing fcPosZero or fcNegZero inference.
- **Expected Issue**: When the integer's sign bit is known and the rest matches zero, the analysis may not infer the specific signed zero class.

### Strategy 4: Test NaN with known sign bit

- **Target**: Bitcast where the value is provably NaN and the sign bit is known
- **Rationale**: When Known.KnownFPClasses = fcNan is set, the sign bit information from Bits.isNonNegative() or Bits.isNegative() should be preserved. The current code sets sign bit before the NaN check, but fcNan includes both positive and negative NaNs. Need to verify the sign bit is correctly maintained.
- **Expected Issue**: The sign bit may be incorrectly constrained or not properly propagated when the value is known to be NaN.

### Strategy 5: Test vector bitcasts with partial element knowledge

- **Target**: Vector bitcast where only some elements have known bits
- **Rationale**: The code uses getScalarType() and DemandedElts for computeKnownBits. For vectors, the analysis should handle per-element knowledge. Testing with vectors where only some elements have known bits could reveal issues with element-wise handling.
- **Expected Issue**: The analysis may incorrectly propagate knowledge across vector elements or fail to handle DemandedElts correctly for vectors.

### Analysis

### Bug Triggering Analysis
The test case triggers a potential issue in the ValueTracking fix for computing fpclass from bitcast. When the integer source has all bits known (sign=0, exp=all 1s, fraction=all 0s), the bitcast should produce +Inf. The fix attempts to detect this by comparing against InfKB which has the sign bit cleared. However, the equality check `Bits == InfKB` requires exact match, and since Bits has sign bit known to be 0 while InfKB has sign bit unknown (Zero has sign bit cleared), the equality check fails. This means fcPosInf is not inferred, only fcInf.

### Fix Weakness Analysis
The fix weakness is in the sign-agnostic matching for Inf/Zero detection. The code clears the sign bit in InfKB.Zero and ZeroKB.Zero to make them sign-agnostic, but then uses exact equality check `Bits == InfKB` which requires all bits to match exactly. This creates a mismatch: if the sign bit is known (either 0 or 1), the equality check will fail because InfKB has the sign bit as unknown (Zero has sign bit cleared, One has sign bit 0).

The fix should either:
1. Use a sign-agnostic equality check that ignores the sign bit
2. Or create separate InfKB for +Inf and -Inf and check against both

This test reveals that the fix doesn't properly infer signed infinity/zero classes when the sign bit is known.
