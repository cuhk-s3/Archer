## Test Strategies

### Strategy 1: Test loop with exactly 2 iterations and last-iteration peeling condition

- **Target**: Create a loop that executes exactly 2 iterations where the last iteration has a unique condition that would be eliminated by peeling. Verify the transformation is correct and doesn't leave a single-iteration loop that could cause issues.
- **Rationale**: The canPeelLastIteration() check requires BTC > 0 (at least 2 iterations). When BTC=1, peeling the last iteration leaves exactly 1 iteration in the main loop. This edge case may expose issues with the remaining loop structure or subsequent optimizations.
- **Expected Issue**: The transformed code may have incorrect semantics when the remaining loop has only 1 iteration, or the optimization may be incorrectly applied when it shouldn't be.

### Strategy 2: Test loop with multiple conditions where one triggers last-iteration peeling and another triggers first-iteration peeling

- **Target**: Create a loop with two conditions: one that can be eliminated by peeling first iterations, and another that can only be eliminated by peeling the last iteration. Check if DesiredPeelCountLast is correctly computed.
- **Rationale**: At line 498, DesiredPeelCountLast is updated with NewPeelCount even when peeling from the beginning succeeds. If one condition sets DesiredPeelCountLast=1 via shouldPeelLastIteration(), and another condition has NewPeelCount>0, line 498 could incorrectly set DesiredPeelCountLast to a value > 1, violating the single-iteration constraint for last-iteration peeling.
- **Expected Issue**: DesiredPeelCountLast may be set to a value > 1, causing peelLoop to be called with PeelCount > 1 and PeelLast = true, which violates the assertion at line 1012.

### Strategy 3: Test exit condition bound underflow when subtracting 1

- **Target**: Create a loop where the exit condition compares against 0 (minimum unsigned value). When peeling the last iteration, the code subtracts 1 from the bound, which would underflow.
- **Rationale**: At lines 1177-1182, the exit condition bound is decremented by 1. If the bound is 0 (for unsigned types), this creates an underflow. The canPeelLastIteration() check doesn't verify that the bound is > 0.
- **Expected Issue**: Integer underflow in the exit condition, causing incorrect loop behavior or infinite loops.

### Strategy 4: Test loop with PHI nodes in exit block that have complex dependencies

- **Target**: Create a loop where the exit block has PHI nodes with values that depend on multiple paths, and verify that formLCSSA correctly handles the transformation when peeling the last iteration.
- **Rationale**: When peeling the last iteration, the code captures exit PHI values at lines 1080-1081 and replaces them at lines 1216-1217. Complex PHI dependencies might not be correctly handled, especially if there are multiple exit paths or the PHI values have uses outside the loop.
- **Expected Issue**: Incorrect value propagation after transformation, leading to wrong results in code that uses the exit values.

### Strategy 5: Test loop where shouldPeelLastIteration returns true but the condition is not actually eliminable

- **Target**: Create a loop where shouldPeelLastIteration() returns true (condition is known at last and second-to-last iterations), but the condition is used in a way that peeling doesn't actually eliminate it (e.g., the condition result is used in a phi node that merges with other values).
- **Rationale**: The shouldPeelLastIteration() function only checks if the predicate is known at specific iterations, but doesn't verify that peeling actually eliminates the compare from the generated code. The compare might still be needed for other purposes.
- **Expected Issue**: Unnecessary peeling transformation that doesn't provide the expected benefit, or worse, incorrect code if the condition is still needed.
