## Test Strategies

### Strategy 1: UnaryOp_FNeg_OutOfBounds

- **Target**: FNeg instruction in loop
- **Rationale**: The fix checks Instruction::isBinaryOp() before accessing NewOps[1], but FNeg is a unary operation. If FNeg somehow reaches this code path with the isBinaryOp check passing incorrectly, accessing NewOps[1] would be out of bounds. Test with FNeg in a vectorizable loop.
- **Expected Issue**: Potential crash or assertion failure due to out-of-bounds array access on NewOps[1] for unary operations

### Strategy 2: ShiftByPoisonAmount

- **Target**: LShr/Shl/AShr with SCEV-constant but runtime-poison shift amount
- **Rationale**: SCEV may determine a shift amount is constant (e.g., 0), but if the actual runtime value could be poison (e.g., due to undefined behavior from another path), the SCEV-based simplification could mask the poison propagation. Test with shift operations where SCEV says the operand is constant but the value has poison-generating conditions.
- **Expected Issue**: Miscompilation where poison values are not properly propagated, leading to undefined behavior being treated as defined

### Strategy 3: FirstOperandConstant_MissingOptimization

- **Target**: Add/Sub/And/Or/Xor with first operand SCEV-constant
- **Rationale**: The fix only simplifies the first operand for Mul, but not for other binary ops. If the first operand is SCEV-constant but the second is not, the VPlan cost model may differ from the legacy cost model, causing different vectorization decisions.
- **Expected Issue**: Vectorization decision mismatch between VPlan and legacy cost model, potentially causing performance regression or missed vectorization opportunities

### Strategy 4: DivRem_SCEVConstant_Divisor

- **Target**: SDiv/UDiv/SRem/URem with SCEV-constant divisor
- **Rationale**: Division and remainder operations are handled in a separate case that falls through. If the divisor is SCEV-constant, the current fix doesn't apply the same simplification, potentially causing cost model differences for these operations.
- **Expected Issue**: Cost model mismatch for division/remainder operations with constant divisors, leading to different vectorization decisions

### Strategy 5: SCEVStaleness_AfterCFGModification

- **Target**: Loop with CFG modifications affecting SCEV cache
- **Rationale**: The subsystem knowledge mentions that SCEV caches can become stale when CFG modifications change the nature of LCSSA PHIs. If SCEV returns a constant for a value that has been invalidated by CFG changes, the fix could incorrectly simplify operands.
- **Expected Issue**: Incorrect constant simplification due to stale SCEV cache, causing miscompilation or crashes during code generation

### Analysis

### Bug Triggering Analysis
The provided test case from the original patch tests the scenario where the second operand of an lshr instruction is known to be constant via SCEV analysis. The shift amount `%ext.0 = sext i8 0 to i32` is computed at runtime but SCEV knows it evaluates to constant 0. The fix ensures that VPlan construction uses SCEV to simplify this operand to a constant, matching the legacy cost model behavior.

### Fix Weakness Analysis
The test successfully verifies that the fix correctly handles the main scenario it was designed for - simplifying SCEV-constant operands in binary operations. Through differential testing with multiple test cases covering all five proposed strategies:

1. **ShiftByPoisonAmount**: Tested with lshr where shift amount is SCEV-constant 0. The transformation is correct - no miscompilation detected.

2. **DivRem_SCEVConstant_Divisor**: Tested division with SCEV-constant divisor. The fix doesn't apply to div/rem (they fall through), but no incorrect behavior was found.

3. **FirstOperandConstant_MissingOptimization**: Tested add/shl with first operand SCEV-constant. The fix intentionally only simplifies first operand for Mul, and no bugs were found for other binops.

4. **UnaryOp_FNeg_OutOfBounds**: Tested FNeg (unary op) in a loop. The `isBinaryOp()` check correctly prevents out-of-bounds access to `NewOps[1]`.

5. **SCEVStaleness_AfterCFGModification**: Tested with CFG containing unreachable blocks. No SCEV staleness issues were detected.

All differential tests showed matching behavior between original and optimized code, confirming the fix is correct for the tested scenarios. The fix successfully aligns VPlan construction with the legacy cost model's SCEV-based constant detection without introducing new bugs.
