## Test Strategies

### Strategy 1: Empty Range Test

- **Target**: trunc-nuw-nsw-flags.ll
- **Rationale**: The getActiveBits() and getMinSignedBits() functions return 0 for empty sets. If the operand's constant range is empty (which can happen in unreachable code paths), the condition '0 <= DestWidth' would always be true, incorrectly setting nuw/nsw flags on the trunc instruction. This could lead to incorrect optimization decisions.
- **Expected Issue**: SCCP incorrectly adds nuw/nsw flags to trunc instructions when the operand has an empty constant range, potentially causing miscompilation or poison value propagation issues.

### Strategy 2: Vector Type Range Analysis Test

- **Target**: trunc-nuw-nsw-flags.ll
- **Rationale**: The test file shows that vector test case range_from_and_nuw_vec does NOT get nuw flag added in the expected output, even though each element is constrained to [0, 65535] which should fit in 16 bits. This suggests the vector type handling in GetRange or the range analysis might not be working correctly for vectors. The fix uses getScalarSizeInBits() but the constant range tracking for vectors might not properly aggregate per-element information.
- **Expected Issue**: SCCP fails to infer nuw/nsw flags on trunc instructions with vector types even when the scalar element ranges would justify the flags, missing optimization opportunities.

### Strategy 3: Full Range Boundary Test

- **Target**: trunc-nuw-nsw-flags.ll
- **Rationale**: When the operand range is the full range of the source type (e.g., full i32 range), getActiveBits() returns the source bit width (32 for i32). If truncating to a smaller type (e.g., i16), the condition '32 <= 16' would be false, correctly not setting the flag. However, edge cases near the boundary (e.g., range [0, 65535] for i32->i16 trunc) need to be tested to ensure getActiveBits() returns exactly 16, not 17 or more due to implementation details.
- **Expected Issue**: Boundary cases where the active bits exactly equal the destination width might be mishandled due to off-by-one errors in getActiveBits() or getMinSignedBits() calculations.

### Strategy 4: Negative Range NSW Test

- **Target**: trunc-nuw-nsw-flags.ll
- **Rationale**: The getMinSignedBits() function computes the max of getSignificantBits() for signed min and max values. For ranges containing negative values, this needs to correctly account for sign extension. A test with a range like [-128, -1] (all negative) truncating to i8 should set nsw, but if the range includes values that would change sign when truncated, nsw should not be set.
- **Expected Issue**: Incorrect nsw flag inference for ranges containing negative values, especially when the range spans across the sign boundary or when sign extension behavior is complex.

### Strategy 5: Both Flags Already Set Test

- **Target**: trunc-nuw-nsw-flags.ll
- **Rationale**: The fix has an early return at line 153-154: 'if (TI->hasNoSignedWrap() && TI->hasNoUnsignedWrap()) return false;'. This correctly skips processing if both flags are already set. However, we should test cases where only one flag is already set to ensure the other flag can still be inferred correctly, and that the partial flag state doesn't interfere with the analysis.
- **Expected Issue**: When only one of nuw/nsw is already set on a trunc, the fix might fail to infer the other flag, or might incorrectly re-set the already-set flag causing redundant processing.
