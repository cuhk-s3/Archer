# EarlyOtherwiseBranch
Model: deepseek-flash
Scope: historical-transformation-program-pair; concrete tested inputs, not a current rustc bug claim or universal proof.

## Elements Frequently Missed
- Treating the old `may_hoist` projection filter as sufficient: it permits Deref-of-reference and Field projections without proving the enum value is valid or the discriminant is computed in all branches.
- Assuming that after UnreachableEnumBranching the `otherwise` being unreachable suffices; some parent targets can still bypass the child discriminant switch, so branch verification remains mandatory.
- Confusing this optimization-soundness condition with ordinary borrow-checker restrictions; the failure mode here is computing a discriminant of uninitialized or invalid enum data (e.g. after unsafe writes of a bad bit pattern), which is UB.
- Allowing a reachable parent `otherwise` because the candidate only "looks like" nested switches; the historical code did exactly this and hoisted `discriminant(Q)` onto paths where it may be invalid.
- Using `opt_data.destination` or `child_targets.otherwise()` as the new equal-switch otherwise: this converts an unlisted/invalid parent discriminant into a defined fallback, changing UB into defined behavior and misrouting valid values.
- Assuming the destination choice is always the child fallback; the shipped code uses `parent_targets.otherwise()`.
- Testing only invalid-enum UB cases, which Miri cannot execute on both sides; a fully valid value that takes the parent otherwise (like x=C,y=C) exposes the same destination bug in an executable pair.
- Conflating destination preservation with the separate reachability guard; both conditions must hold for the rewrite.
- Folding when the inner matched constant differs from the outer value: `opt5_failed` uses `(3, 2) => 6`, and an over-broad fold would hoist `Ne(x, y)` true and return the otherwise value 0 instead of 6.
- Folding places of different types: `opt5_failed_type` uses `x: u32, y: u64`; comparing them would be ill-typed and semantically wrong.
- Accepting `Operand::Move(place)` on the scalar path: a move invalidates the place before the hoisted comparison; the scalar path requires `Operand::Copy(place)`.
- Dropping the `empty_unreachable` guard for discriminant hoisting: copying/comparing a scalar is safe, but hoisting `Rvalue::Discriminant` can evaluate an invalid enum value.
- Using `child_targets.otherwise()` unconditionally as the destination; when no hoist is needed and the parent otherwise is reachable, it must be `targets.otherwise()` so unequal values route correctly.
- Requiring the scalar child block to contain a discriminant assignment; the scalar case has zero statements, while the discriminant case has exactly one.
- Treating the presence of `Ne(` as proof of correctness; the negative controls must show `// CHECK-NOT: Ne(` to confirm rejection.
- Diagnosing this as a borrow-checking or Tree Borrows problem: the unoptimized program passes Miri with Tree Borrows; the reported failure is specifically a dead-local access.
- Working around the self-loop by creating an extra indirect basic block to hold StorageDead; the accepted fix removes the storage markers for the created temps entirely.
- Trusting a retained test name or stale comment in a mir-opt diff; verify the actual assignments and absence of storage markers around the hoisted temp.
- Generalizing the marker removal to other passes or to unrelated CFG properties; the relevant wrongness is the placement/ordering of `StorageDead(comp_temp)` relative to `switchInt(move comp_temp)` when a target is the parent block.
- Attributing an EarlyOtherwiseBranch MIR diff to a bug or fix in EarlyOtherwiseBranch when it is merely reordered input MIR from match lowering's corrected binding order (deepest-first, same-depth source order).
- Attributing SimplifyCfg/EarlyOtherwiseBranch block-label diffs to the single-pass SwitchInt change instead of the real bug: accepting a later constant as a SwitchInt success arm when an earlier range already sorted into the failure branch covers it.
- Updating expected block labels/switch arm order without first confirming the source-level match semantics are unchanged.
- Confusing this cross-pass attribution with the real EarlyOtherwiseBranch invariants (unreachable parent otherwise, parent-otherwise destination, scalar folding conditions, storage-marker placement).

## Patterns Not Well Handled

### Hoist a child discriminant only when the parent otherwise is empty+unreachable and every reachable parent successor computes it
EarlyOtherwiseBranch rewrites a parent `SwitchInt` over `discriminant(P)` whose case blocks contain child `SwitchInt`s over `discriminant(Q)` into one hoisted child discriminant, an `Ne` comparison against the parent discriminant, and a single switch. That rewrite is only sound if the child discriminant is computed on every reachable path reaching the hoist point. The supplied fix replaces projection-based reasoning (`may_hoist` on Deref/Field/Downcast) with a conservative reachability guard: the parent `otherwise` must be an empty unreachable block, and each parent target must verify as a child discriminant switch. The historical justification is explicit: "An invalid enum discriminant can come from anywhere. We have to check to see if all successors contain the discriminant statement." and "Hoisting the `discriminant(Q)` out of the `A` arm causes us to compute the discriminant of an invalid value, which is UB." The shipped guard is `if !bbs[targets.otherwise()].is_empty_unreachable() {` returning no candidate.
Preconditions: Parent switch has an `otherwise` branch and at least one child case block begins with a `SwitchInt` over the child discriminant with matching value targets (the candidate shape).; `bbs[targets.otherwise()].is_empty_unreachable()` holds: no statements and an `Unreachable` terminator.; Every parent target branch passes `verify_candidate_branch` as a child discriminant switch over the same child place with the expected value mapping; a parent case that reaches fallback directly must block the rewrite.; Projection kind inspection (Deref-of-reference, Field, Downcast rejection) is not a soundness argument on its own; validity/initialization of the hoisted place at the hoist point is what matters.; Tests may need `-Zmir-enable-passes=+UnreachableEnumBranching` so the parent `otherwise` becomes unreachable and the candidate is exposed.
Pitfalls: Treating the old `may_hoist` projection filter as sufficient: it permits Deref-of-reference and Field projections without proving the enum value is valid or the discriminant is computed in all branches.; Assuming that after UnreachableEnumBranching the `otherwise` being unreachable suffices; some parent targets can still bypass the child discriminant switch, so branch verification remains mandatory.; Confusing this optimization-soundness condition with ordinary borrow-checker restrictions; the failure mode here is computing a discriminant of uninitialized or invalid enum data (e.g. after unsafe writes of a bad bit pattern), which is UB.; Allowing a reachable parent `otherwise` because the candidate only "looks like" nested switches; the historical code did exactly this and hoisted `discriminant(Q)` onto paths where it may be invalid.
Test strategy: Use MIR unit tests tagged `//@ unit-test: EarlyOtherwiseBranch` with `//@ compile-flags: -Zmir-enable-passes=+UnreachableEnumBranching`. Positive tests FileCheck for a hoisted child `discriminant`, an `Ne` between parent and child discriminants, and a `switchInt` on the comparison (e.g. `[[CMP_LOCAL]] = Ne([[LOCAL1]], move [[LOCAL2]])` then `switchInt(move [[CMP_LOCAL]])`). Negative soundness tests must assert `// CHECK-NOT: Ne` after the parent discriminant, including the added `opt1` case commented `// We can't optimize it because y may be an invalid value.` plus existing `no_downcast` and `no_deref_ptr` cases. Cover `Option`/custom `Option2`, 2- and 3-element tuples, references, downcasts, and pointer dereferences so projection variants are exercised.

### Preserve the parent otherwise on the newly created equal-variant switch
When EarlyOtherwiseBranch creates the replacement `switchInt` over the parent discriminant for the equal variants, its fallback must be `parent_targets.otherwise()`, not the child fallback or `opt_data.destination`. The historical transformation used the child fallback as the new equal-switch otherwise, which could route an unlisted/invalid parent discriminant to a defined fallback instead of preserving the parent's unreachable/UB successor. The fix shows the exact substitution: `-            let eq_targets = SwitchTargets::new(eq_new_targets, opt_data.destination);` replaced by `let eq_targets = SwitchTargets::new(eq_new_targets, parent_targets.otherwise());`. The supplied concrete pair isolates this destination error with fully valid, initialized values: parent targets A(0)/B(1) each dispatch to a child switch on y with fallback 5, while the wildcard parent arm for C is the parent otherwise returning 1; for x=C,y=C the original returns 1 but the wrong transformation returns 5. This demonstrates that the destination error is independently observable even without invalid-enum UB.
Preconditions: The candidate matches the early-otherwise shape so the pass actually creates a new equal-variant `switchInt` over the parent discriminant.; A parent discriminant value exists that is not one of the parent switch's listed targets (e.g. x=C when the parent switch lists only A and B).; The child fallback/destination differs from the parent otherwise target.
Pitfalls: Using `opt_data.destination` or `child_targets.otherwise()` as the new equal-switch otherwise: this converts an unlisted/invalid parent discriminant into a defined fallback, changing UB into defined behavior and misrouting valid values.; Assuming the destination choice is always the child fallback; the shipped code uses `parent_targets.otherwise()`.; Testing only invalid-enum UB cases, which Miri cannot execute on both sides; a fully valid value that takes the parent otherwise (like x=C,y=C) exposes the same destination bug in an executable pair.; Conflating destination preservation with the separate reachability guard; both conditions must hold for the rewrite.
Test strategy: Inspect the MIR diff and assert that the new equal-variant switch's otherwise is the original parent unreachable block (e.g. `otherwise: bb9` where `bb9: unreachable`) rather than the child fallback. Add a runnable case where a parent discriminant not listed in the parent switch takes the parent otherwise (e.g. `C` arm returning 1) and verify the result is 1, not the child fallback value (5). Keep the positive FileCheck for the hoisted `Ne`/`switchInt` shape so a pass that simply refuses the rewrite is distinguishable from one with the correct destination.

### Scalar-pair folding requires same types, zero statements, Copy operand, exact value correspondence, and correct destination selection
EarlyOtherwiseBranch was extended from only hoisting `Rvalue::Discriminant` to also folding nested scalar matches, e.g. `match (x, y) { (1,1)=>4, (2,2)=>5, (3,3)=>6, _=>0 }`. For a child block with no statements whose `SwitchInt` directly tests `Operand::Copy(place)`, the pass hoists `Ne(parent, child)` before the parent switch. The extension is safe only under a conjunction of structural conditions, all quoted from the shipped code: `let need_hoist_discriminant = bbs[child].statements.len() == 1;`, `if *switch_op != Operand::Copy(place) {`, `if child_ty != parent_ty { return None; }`, `target_value == value`, `if destination != targets.otherwise() { return false; }`. Crucially the old UB guard for discriminant hoisting is retained: "Hoisting the `discriminant(Q)` out of the `A` arm causes us to compute a discriminant of an invalid value, which is UB." The destination is `let destination = if need_hoist_discriminant || bbs[targets.otherwise()].is_empty_unreachable()` ... else `targets.otherwise()`; so copying/comparing a scalar needs no UB guard, but discriminant hoisting still requires the parent otherwise to be empty+unreachable.
Preconditions: Parent and child places have the same type (`child_ty == parent_ty`).; Scalar/no-hoist path: the child block has no statements (`if !branch.statements.is_empty() { return false; }`) and its switch operand is `Operand::Copy(place)`, not `Move`.; Discriminant path: exactly one `StatementKind::Assign(box (discr_place, Rvalue::Discriminant(from_place)))` with `from_place == place`, `discr_place.projection.is_empty()`, and `switch_op == Operand::Move(discr_place)`.; Each outer target's child falls through to the chosen destination: `if destination != targets.otherwise() { return false; }`.; Each child switch has exactly one matched value equal to the outer value: `let (Some((target_value, _)), None) = (iter.next(), iter.next()) else { return false; }; target_value == value`.; For the discriminant-hoisting path, `bbs[targets.otherwise()].is_empty_unreachable()` must still hold; the guard is only relaxed for the scalar no-hoist path.
Pitfalls: Folding when the inner matched constant differs from the outer value: `opt5_failed` uses `(3, 2) => 6`, and an over-broad fold would hoist `Ne(x, y)` true and return the otherwise value 0 instead of 6.; Folding places of different types: `opt5_failed_type` uses `x: u32, y: u64`; comparing them would be ill-typed and semantically wrong.; Accepting `Operand::Move(place)` on the scalar path: a move invalidates the place before the hoisted comparison; the scalar path requires `Operand::Copy(place)`.; Dropping the `empty_unreachable` guard for discriminant hoisting: copying/comparing a scalar is safe, but hoisting `Rvalue::Discriminant` can evaluate an invalid enum value.; Using `child_targets.otherwise()` unconditionally as the destination; when no hoist is needed and the parent otherwise is reachable, it must be `targets.otherwise()` so unequal values route correctly.; Requiring the scalar child block to contain a discriminant assignment; the scalar case has zero statements, while the discriminant case has exactly one.; Treating the presence of `Ne(` as proof of correctness; the negative controls must show `// CHECK-NOT: Ne(` to confirm rejection.
Test strategy: Use MIR dump tests with `// EMIT_MIR early_otherwise_branch.opt5.EarlyOtherwiseBranch.diff` plus CHECK-LABEL/CHECK/CHECK-NOT. Positive `opt5`: `match (x: u32, y: u32) { (1,1)=>4, (2,2)=>5, (3,3)=>6, _=>0 }` must show `_6 = Ne(copy (_3.0: u32), copy (_3.1: u32));` and `switchInt(move _6) -> [0: bb6, otherwise: bb1];`. Negative controls: `opt5_failed` with `(3, 2) => 6` and `opt5_failed_type(x: u32, y: u64)` must retain nested switches and satisfy `// CHECK-NOT: Ne(`. Add analogous MIR negatives for a non-`Copy`/`Move` child switch and for child-vs-parent otherwise destinations that differ. Run the existing runtime `main` calls only as a smoke test; do not claim execution or reproduction.

### Do not synthesize StorageLive/StorageDead for hoisted temps; a target may be the parent block
EarlyOtherwiseBranch creates temps for the hoisted child discriminant and comparison. The historical code emitted `StorageDead(comp_temp)` at `statement_index: 0` of every generated switchInt target. When one target is the same block that ends in the new `switchInt` (a self-loop, e.g. the fallback arm `_ => bb1` where bb1 is the match block), the inserted `StorageDead` lands before `switchInt(move _temp)`, producing a use of a dead local. The issue title is "EarlyOtherwiseBranch can insert storage markers incorrectly, creating use of a dead local" with the runtime symptom "error: Undefined Behavior: accessing a dead local variable". The accepted fix is stated as: "The first commit add `StorageDead` by creating new indirect BB that makes CFG more complicated, but I think it's better to just not create storage marks." The corrected diff contains only `_2 = Ne(copy _1, copy _1);` followed by `switchInt(move _2) -> [0: bb3, otherwise: bb1];`, with no `StorageLive`/`StorageDead` for the new temps.
Preconditions: EarlyOtherwiseBranch matches a candidate that requires hoisting the second discriminant/comparison into a temp.; A new temporary holding the comparison is moved into the generated `switchInt`.; One of the generated switchInt targets equals the parent block containing that switchInt (self-referential target), which is what turns index-0 insertion into an ordering bug.
Pitfalls: Diagnosing this as a borrow-checking or Tree Borrows problem: the unoptimized program passes Miri with Tree Borrows; the reported failure is specifically a dead-local access.; Working around the self-loop by creating an extra indirect basic block to hold StorageDead; the accepted fix removes the storage markers for the created temps entirely.; Trusting a retained test name or stale comment in a mir-opt diff; verify the actual assignments and absence of storage markers around the hoisted temp.; Generalizing the marker removal to other passes or to unrelated CFG properties; the relevant wrongness is the placement/ordering of `StorageDead(comp_temp)` relative to `switchInt(move comp_temp)` when a target is the parent block.
Test strategy: Add a `//@ test-mir-pass: EarlyOtherwiseBranch` custom-MIR test where an arm loops back to the same block, e.g. `target_self(val: i32)` with `match val { 0 => bb2, _ => bb1, }` then `match val { 0 => bb3, _ => bb1, }`. Check for `Ne(` followed immediately by `switchInt` (`// CHECK: Ne(` / `// CHECK-NEXT: switchInt`) and assert no `StorageLive`/`StorageDead` for the new temp appears in the parent block or target blocks; the corrected diff shows `_2 = Ne(copy _1, copy _1);` then `switchInt(move _2) -> [0: bb3, otherwise: bb1];`. Alternatively run the reduced self-looping program under Miri with `-Zmir-enable-passes=+EarlyOtherwiseBranch` to catch the dead-local use. A concrete executable pair should preserve the original false->bb3 path versus the buggy dead-temp read taking the otherwise/self-loop path, with any iteration bound treated as a shared finite observation window, not part of the rewrite.

### Distinguish EarlyOtherwiseBranch test-expectation churn caused by upstream match lowering from changes to the pass itself
Two supplied historical cases changed EarlyOtherwiseBranch (and SimplifyCfg) MIR expectations even though the actual fix was in match lowering. In the binding-order fix, MIR-opt tests for EarlyOtherwiseBranch were updated only because corrected match lowering reorders `StorageLive`/assignment pairs in the input MIR; the pass invariant is unchanged. In the SwitchInt single-pass fix, EarlyOtherwiseBranch and SimplifyCfg expectation diffs reflect block allocation/renumbering — e.g. `switchInt(move _8) -> [0: bb2, 1: bb4, otherwise: bb1];` becoming `switchInt(move _8) -> [0: bb3, 1: bb2, otherwise: bb1];` — not a new optimization invariant. The reusable lesson is to attribute diffs to their source: `tests/mir-opt/early_otherwise_branch.opt2.EarlyOtherwiseBranch.diff` and `tests/mir-opt/match_arm_scopes.complicated_match.panic-abort.SimplifyCfg-initial.after-ElaborateDrops.after.diff` show downstream churn, whereas the semantic bugs are in match lowering (binding order: "and bindings at the same depth stay in source order"; single-pass SwitchInt: "Beware: there might be some ranges sorted into the failure case; we must not add a success case that could be matched by one of these ranges.").
Preconditions: The change originates in match lowering (binding order/`@`-pattern accumulation, or single-pass SwitchInt candidate sorting) rather than in EarlyOtherwiseBranch's candidate detection or rewrite.; An EarlyOtherwiseBranch or SimplifyCfg mir-opt expectation diff is present.; The MIR-level difference can be explained entirely by reordered StorageLive/assignment statements in the pass input, or by block renumbering/branch-arm ordering, while the source-level match semantics are unchanged.
Pitfalls: Attributing an EarlyOtherwiseBranch MIR diff to a bug or fix in EarlyOtherwiseBranch when it is merely reordered input MIR from match lowering's corrected binding order (deepest-first, same-depth source order).; Attributing SimplifyCfg/EarlyOtherwiseBranch block-label diffs to the single-pass SwitchInt change instead of the real bug: accepting a later constant as a SwitchInt success arm when an earlier range already sorted into the failure branch covers it.; Updating expected block labels/switch arm order without first confirming the source-level match semantics are unchanged.; Confusing this cross-pass attribution with the real EarlyOtherwiseBranch invariants (unreachable parent otherwise, parent-otherwise destination, scalar folding conditions, storage-marker placement).
Test strategy: When an EarlyOtherwiseBranch or SimplifyCfg mir-opt diff appears, first classify it by comparing the pass input MIR. If only `StorageLive`/assignment pairs are reordered (e.g. `_9` before `_8` for a two-element case, `_11`, `_12`, `_13` reversed for a three-element tuple), treat it as match-lowering binding-order churn and update the expectation without claiming a pass change. If block labels or switch arm ordering changed (e.g. `[0: bb2, 1: bb4, otherwise: bb1]` -> `[0: bb3, 1: bb2, otherwise: bb1]`), verify the semantic match behavior with a run-pass test such as `match 1 { 10 => unreachable!(), 0..=5 => {}, 1 => unreachable!(), _ => unreachable!(), }` under `#![allow(unreachable_patterns)]`. For binding-order churn, keep the run-pass UI tests (e.g. `tests/ui/pattern/bindings-after-at/`) as the semantic oracle and update `early_otherwise_branch*.diff` only after confirming binding order deepest-first with same-depth source order.
