- Do not erase source info for all unreachable blocks; only set the erasure when deduplicated_unreachable is true.
- Do not conflate this with SimplifyLocals; the relevant path is SimplifyCfg/remove_dead_blocks.
- The fix deliberately erases even when all deduplicated blocks share identical source info: "Technically we don't need to erase the source information if all the deduplicated blocks have identical source information, but tracking that seems like more effort than it's worth."

- Do not claim runtime reproduction or compiler execution; the supplied material is source/patch inspection.
- Mutating the start block is distinct from mutating saved terminator targets; the changed flag must cover both.
- Set changed only on a real difference (`*start != last`), not unconditionally, to preserve accurate change reporting.
- Recording the start rewrite without marking change can leave callers/fixpoint iteration believing the CFG is unchanged and stopping early.
- Do not choose the whole match's start block: it is on the success path of all candidates and would create a loop. Choose the earliest D-success block that does not also lead to C.
- Do not keep the direct pre-binding-to-pre-binding target; that is the too-coarse historical edge that lets borrowck reach bindings before the deref temporary is initialized.
- Do not work around the issue by calling `deref()` a second time; the source notes this opens the door to soundness issues if the deref implementation is weird.
- Propagate `false_edge_start_block` through subcandidates and merged or-pattern subcandidates; the code asserts `leaf_candidate.false_edge_start_block.is_some()`.
- Update guard-otherwise false edges as well as ordinary pre-binding false edges; both use the next-candidate start block after the fix.
- NLL tests intentionally preserve errors even when the real lowering proves an arm or guard unreachable; do not weaken those expectations while fixing deref-temporary precision.
- Do not treat fewer SwitchInts as sufficient: moving failure edges across an or-pattern simplification can select the wrong next candidate.
- Do not expand an or-pattern candidate together with candidates that follow it unless the or-pattern is that candidate's only remaining match pair.
- Do not skip trying the second or-alternative when a guard is present; unlike the no-guard case, the failure block may be reached by guard failure.
- Dummy or-patterns such as `_ | _` can still force a guard to run multiple times, so guard side effects/counts are observable.
- Do not naively sort identical tested values together and share failure paths; the `simplification_subtleties` test uses `(1 | 2, false | false)` followed by `(2, _)` specifically to catch this.
- The `otherwise_block` is now needed for all selected candidates, so retaining the old guard-only assignment would lose the pre-binding failure path.
- Do not infer semantic change only from local numbering or block-number renumbering. Reversing sub-branches swaps StorageLive/StorageDead temporaries (e.g. `_9`/`_10` vs `_12`/`_13`) and branch targets; the meaningful change is which source-order sub-branch supplies binding/drop order, such as `_5 = copy (_2.0: bool)` versus `_5 = copy (_2.1: bool)`.
- Do not treat or-pattern bindings as rightmost/last. The corrected rule is to inline the or-alternatives chosen in a sub-branch as if they appeared at that point in the arm pattern.
- Preserve the `@` rule: the right-hand side of `@` comes before the binding on the left. The bind-by-copy-or-pat test changes from `//@ known-bug: unknown` plus E0382 errors to `//@ run-pass`.
- Guards still need drop scheduling during guard binding so StorageDead is emitted on guard failure/break paths; the new code always schedules storage drops, then clears the top scope for non-final lowered sub-branches so only the final (source-first) sub-branch supplies arm drop order.
- Only insert the `FromOrPattern` placeholder when the first alternative has bindings (check `!pats[0].extra_data.bindings.is_empty()`), so or-patterns simplified by `merge_trivial_subcandidates` are skipped.
- Ill-formed or-patterns with mismatched bindings, such as `(x, _ | y)` and `x | _`, can leave no matching subcandidate bindings; the patch emits a `delayed_bug("mismatched or-pattern bindings but no error emitted")` rather than silently dropping bindings.
- Binding modes may differ between alternatives. The dropck test reports the eager by-ref lifetime error on the first alternative (`&Err(short4) | Ok(short4)`) instead of the previous alternative (`Ok(short3) | &Err(short3)`), so tests must not assume the old alternative wins.
- Do not attribute the lowering regression to SimplifyCfg or EarlyOtherwiseBranch; their changed expectations are downstream block-number/CFG-shape churn.
- A range already sorted into the failure branch is not safe to ignore while later success arms are discovered; the candidate set is still being formed.
- Containment that is unknown (`range.contains` returns `None`) must be treated conservatively as a possible conflict, as the fix does with `None | Some(true)`.
- The usize-to-TestBranch enum replacement is bookkeeping; the historical incorrect transformation is the single-pass ordering/acceptance of a later covered constant, not the enum itself.
- The regression source intentionally allows unreachable patterns because `1` is covered by the earlier `0..=5` arm; a compile-only test is weaker than a run-pass test that would panic if the wrong arm were selected.
- Update SimplifyCfg expected block labels/switch arm ordering only after confirming the source-level semantics are unchanged; do not infer a new SimplifyCfg invariant from renumbering.

## Patterns Not Well Handled

### SimplifyCfg unreachable-block deduplication must erase the surviving terminator's source info
In SimplifyCfg's remove_dead_blocks, when a later unreachable block is deduplicated into an already-kept unreachable block, the kept block conceptually represents multiple source locations. The surviving block's terminator SourceInfo must therefore be rewritten to DUMMY_SP/OUTERMOST_SOURCE_SCOPE whenever at least one unreachable block was deduplicated. The historical incorrect transformation kept the first unreachable block's original span/scope, which can make a debugger map a breakpoint to the wrong instruction. The erasure is conditional: it applies only when deduplication actually occurred, not to every unreachable block.
Preconditions: SimplifyCfg::remove_dead_blocks runs on a MIR body containing unreachable basic blocks.; More than one unreachable block reaches deduplication such that one is kept and another is replaced by it (kept_unreachable != used_bb).; The surviving unreachable block can survive into compiled code/debug info, making its source mapping observable.
Pitfalls: Do not erase source info for all unreachable blocks; only set the erasure when deduplicated_unreachable is true.; Do not conflate this with SimplifyLocals; the relevant path is SimplifyCfg/remove_dead_blocks.; The fix deliberately erases even when all deduplicated blocks share identical source info: "Technically we don't need to erase the source information if all the deduplicated blocks have identical source information, but tracking that seems like more effort than it's worth."; The change rewrites the kept terminator's source_info (span DUMMY_SP, scope OUTERMOST_SOURCE_SCOPE); it does not remove the kept unreachable block itself.; Do not claim runtime reproduction or compiler execution; the supplied material is source/patch inspection.
Test strategy: Construct MIR where multiple deduplicated unreachable blocks carry distinct source spans, run SimplifyCfg, and inspect the surviving unreachable block's terminator source info; assert it is DUMMY_SP/OUTERMOST_SOURCE_SCOPE. Use a differential input where no unreachable blocks are deduplicated and verify its source info is preserved. For debug-info coverage, check that a breakpoint requested on the erased location is not mapped to the surviving unreachable instruction. Inspect the retained test expectation rather than assuming a replacement pass is wrong.

### SimplifyCfg goto-chain collapse must mark `changed` when the start block moves
CfgSimplifier collapses a chain of single-target Goto terminators. It walks to the chain's final block (`let last = current;`) and rewrites the start block with `*start = last;`. The start mutation is a separate observable modification from the saved terminator rewrites, so the pass must record `*changed |= *start != last;` immediately before assigning. The historically incorrect transformation updated the start block without setting the changed flag, so callers/fixpoint iteration could treat an actually modified CFG as unchanged and stop before reaching a stable form. The flag should be set only when the start value really differs from the collapsed destination.
Preconditions: The CFG contains a goto chain followed to its final target (`current = target` in the collapse loop).; The rewritten start value differs from the chain's final block (`*start != last`).; The caller relies on the `changed` flag to decide whether MIR was modified or whether another simplification iteration is needed.
Pitfalls: Mutating the start block is distinct from mutating saved terminator targets; the changed flag must cover both.; Set changed only on a real difference (`*start != last`), not unconditionally, to preserve accurate change reporting.; Recording the start rewrite without marking change can leave callers/fixpoint iteration believing the CFG is unchanged and stopping early.
Test strategy: Add a focused MIR/unit regression around CfgSimplifier::collapse_goto_chain with two inputs that differ only in the start-chain shape: one where the start already equals the final goto destination (changed must be false) and one where it points to an intermediate goto (changed must be true, start must move to the final block). The supplied patch itself contains only the compiler change, so no specific test filename can be cited.

### SimplifyCfg-initial falseEdge targets must be the earliest next-candidate success block, not the next pre-binding block
Match lowering inserts false edges so borrowck does not see the real decision-tree structure. The historical implementation linked a candidate C's pre-binding block directly to the next candidate D's pre-binding block (`prev.next_candidate_pre_binding_block = leaf_candidate.pre_binding_block;`). That is too coarse: D's success path may initialize a temporary, notably the result of `deref()`, before D's pre-binding block, so borrowck can see a binding reached before its temporary is initialized. The corrected transformation targets D's `false_edge_start_block`, the earliest D-success block that does not also lead to C, and propagates it through subcandidates/merged or-pattern subcandidates; guard-otherwise false edges use the same corrected target. SimplifyCfg-initial MIR snapshots expose these `falseEdge -> [real: ..., imaginary: ...]` targets.
Preconditions: Ordered candidates/leaves are linked by false edges: candidate C has a next-candidate target and D is its successor.; D's success path initializes a temporary before its pre-binding block, notably the result of `deref()`, and D's binding is established only after the pre-binding block.; The false-edge target is D's pre-binding block rather than the earliest D-success block that does not also lead to C.; Borrowck is consuming the fake CFG produced by match lowering; exact targets are checkable in built/SimplifyCfg-initial MIR dumps.
Pitfalls: Do not choose the whole match's start block: it is on the success path of all candidates and would create a loop. ### Fewer SwitchInts in SimplifyCfg-initial or-pattern MIR is not sufficient; failure routing must be preserved
Match lowering can expand leading or-pattern candidates only up to the first candidate that has additional match pairs, then process expanded candidates before the remaining candidates. The historical approach split only when the candidate's sole match pair was an Or; arms with more than one or-pattern were compiled on their own. The corrected rule is that or-pattern alternatives may be processed alongside candidates that precede them, but not candidates that follow them, unless the or-pattern is the candidate's only remaining match pair. This matters because or-pattern simplification branches all alternatives' success paths to the same block; if a later candidate is processed in the same expanded set, a failed test no longer knows which alternative succeeded and cannot route its failure edge to the correct remaining candidate. `finalize_or_candidate` must also not skip the next alternative when a leaf has a guard, because guard failure can reach that leaf's `otherwise_block`.
Preconditions: The first match pair of a candidate is `TestCase::Or`.; A candidate with more than one remaining match pair bounds the expansion set; candidates after it must remain in `remaining_candidates` and be processed from `remainder_start`.; After expansion, each expanded candidate is finalized with `finalize_or_candidate`, which merges trivial subcandidates and then appends leftover match pairs to every leaf.; For leftover match pairs, the failure target is the last leaf's `otherwise_block`; if a leaf has a guard, use that leaf's own `otherwise_block` instead.; `select_matched_candidate` must set `candidate.otherwise_block` for every matched candidate, not only guarded ones, since a nested candidate can also fail to match.; `merge_trivial_subcandidates` refuses to merge when the candidate has a guard or any subcandidate has non-empty `extra_data` (bindings).
Pitfalls: Do not treat fewer SwitchInts as sufficient: moving failure edges across an or-pattern simplification can select the wrong next candidate.; Do not expand an or-pattern candidate together with candidates that follow it unless the or-pattern is that candidate's only remaining match pair.; Do not skip trying the second or-alternative when a guard is present; unlike the no-guard case, the failure block may be reached by guard failure.; Dummy or-patterns such as `_ | _` can still force a guard to run multiple times, so guard side effects/counts are observable.; Do not naively sort identical tested values together and share failure paths; the `simplification_subtleties` test uses `(1 | 2, false | false)` followed by `(2, _)` specifically to catch this.; The `otherwise_block` is now needed for all selected candidates, so retaining the old guard-only assignment would lose the pre-binding failure path.

### SimplifyCfg snapshot block renumbering from upstream match lowering is not a SimplifyCfg invariant change
When match lowering changes block allocation, label/arm ordering in SimplifyCfg (and EarlyOtherwiseBranch) MIR expectations can churn without any change to SimplifyCfg's own optimization invariant. A source-backed cross-pass example is the single-pass SwitchInt candidate sort: before, two-pass lowering would not accept a later constant covered by an earlier range; in a naive single pass, an earlier range can be sorted into the failure branch and a later constant contained in it then wrongly accepted as a success arm. That is a match-lowering ordering/acceptance issue, not a SimplifyCfg transformation. The changed SimplifyCfg snapshot expectations in that work show renumbered blocks such as `[0: bb2, 1: bb4]` becoming `[0: bb3, 1: bb2]`, reflecting allocation/renumbering rather than a new pass rule. When reviewing SimplifyCfg snapshots, verify source-level semantics before updating labels or arm ordering.
Preconditions: MIR snapshots from SimplifyCfg/EarlyOtherwiseBranch are produced after match lowering allocates blocks differently.; SwitchInt arms or block labels are renumbered even though the source-level match semantics are intended to stay the same.; The candidate list can contain a range before a constant it contains, with no earlier constant inside that range.
Pitfalls: Do not attribute the lowering regression to SimplifyCfg or EarlyOtherwiseBranch; their changed expectations are downstream block-number/CFG-shape churn.; A range already sorted into the failure branch is not safe to ignore while later success arms are discovered; the candidate set is still being formed.; Containment that is unknown (`range.contains` returns `None`) must be treated conservatively as a possible conflict, as the fix does with `None | Some(true)`.; The usize-to-TestBranch enum replacement is bookkeeping; the historical incorrect transformation is the single-pass ordering/acceptance of a later covered constant, not the enum itself.; The regression source intentionally allows unreachable patterns because `1` is covered by the earlier `0..=5` arm; a compile-only test is weaker than a run-pass test that would panic if the wrong arm were selected.; Update SimplifyCfg expected block labels/switch arm ordering only after confirming the source-level semantics are unchanged; do not infer a new SimplifyCfg invariant from renumbering.
