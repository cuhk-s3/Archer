# ConstPropLint
Model: deepseek-flash
Scope: historical-transformation-program-pair; concrete tested inputs, not a current rustc bug claim or universal proof.

## Elements Frequently Missed
- Removing the promoted guard raises duplicate diagnostics: 'This PR increases the number of duplicate diagnostics emitted (because the same operator might get linted in both the promoted MIR and the main MIR).' Tests normalize with `-Z deduplicate-diagnostics=yes` and note 'duplicate diagnostic emitted due to `-Z deduplicate-diagnostics=no`'.
- Optimization level changes which promotions/paths get linted, so a single-revision test is insufficient; the regression test uses `noopt`, `opt`, and `opt_with_overflow_checks`.
- The fix changes acceptance: 'programs containing the above mentioned overflowing promoteds that were accepted earlier will now be rejected'; old tests asserting passing behavior (e.g. `promoted_overflow_opt.rs`) had to be removed or amended.
- Do not conflate const-item evaluation errors (`error[E0080]: evaluation of constant value failed`) with the codegen-time lint (`this arithmetic operation will overflow` / `this operation will panic at runtime`).
- Pointer-width-dependent shift counts need normalization (`shift left by (64|32)_usize` -> `%BITS%`) so tests pass on 32-bit and 64-bit targets.
- Do not treat the transformed-vs-source pair as proof that a compiler was built or that the bug was reproduced; the paired harness only encodes the promoted guard's presence/absence.
- Blanket rejection of all static access is too strong: reading an immutable static in a const is allowed under `const_refs_to_static` (run-pass `const_refs_to_static.rs`).
- Allowing all static access is unsound: reads from `static mut` or interior-mutable statics (`SyncUnsafeCell`, `AtomicUsize`) must be rejected because their value can differ at runtime.
- Creating a pointer/reference is not reading through it: `const C2: *const i32 = unsafe { std::ptr::addr_of!(S_MUT) };` is allowed, but `const C2_READ: () = unsafe { assert!(*C2 == 0); };` must fail with `constant accesses mutable global memory`.
- Validation, not just evaluation, must reject const final values pointing into mutable memory; otherwise const pattern matching can observe mutable data (`constructing invalid value: encountered reference to mutable memory in `const``).
- Extern statics cannot be validated at compile time; a const value referencing an `extern` static must be rejected via `ConstRefToExtern` rather than silently accepted.
- Do not copy the static-initializer permission to consts: statics may read mutable global memory, consts may not.
- Do not confuse the feature-gate diagnostic change with the semantic permission; the gate still must be enabled and mutability checks still apply.
- The paired harness demonstrates the unsound alternative concretely: compile-time propagation of a mutable-static read (returning initial value + 1) versus the runtime read of the mutated value; both are defined executions that merely differ in value.
- Do not fold `NullOp::DebugAssertions` in ConstPropLint or GVN before monomorphization: the folded value would reflect the defining crate's debug-assertion setting, not the caller's.
- Do not guard the unsafe-precondition check with expansion-time `cfg!(debug_assertions)`; the guard must survive into MIR and be resolved at codegen/monomorphization.
- Do not make the runtime `precondition_check` generic; it is intentionally monomorphic, `#[inline(never)]`, and `#[rustc_nounwind]` to avoid code-size duplication and to enable the nounwind optimization.
- In `InstSimplify`, only mark the unwind edge `UnwindAction::Unreachable` for nounwind calls; closure (`Abi::RustCall`) and coroutine (`Abi::Rust`) ABIs must be classified correctly and the call itself must remain.
- Because `assume` codegen is skipped for `OptLevel::No` and `OptLevel::Less`, tests expecting an emitted or optimized `assume` must pin optimization/debug-assertion flags.
- MIR tests are sensitive to debug assertions and panic strategy: the new checks add `cfg!(debug_assertions)` branches and `precondition_check` calls, so tests may need `-Cdebug-assertions=no` or `EMIT_MIR_FOR_EACH_PANIC_STRATEGY`.
- Treat the paired demonstration as a model of the historical early-fold error, not as proof that the modern compiler is wrong or that a build was reproduced.

## Patterns Not Well Handled

### ConstPropLint must lint promoted MIR bodies, not just main-function MIR
ConstPropLint detects arithmetic overflow and unconditional-panic operations in MIR. A body derived from const promotion (`body.source.promoted.is_some()`) historically bypassed the pass via an early return whose rationale was that promoteds 'will be evaluated by miri and produce its errors there'. That filter suppressed diagnostics for enforced-const operations living in promoted bodies, e.g. `&(1u8 << 8)` or `format_args!("{}", 1 << 32)`. The corrected behavior removes the promoted-source guard so promoted and non-promoted forms lint consistently. As the source states: 'What I have done here is simply enabled `ConstPropLint` to run on promoted bodies by removing the relevant `if` check.' and 'After this change _all_ promoted arithmetic operators will lint _in both non-optimized and optimized builds_.'
Preconditions: The MIR body under lint has a promoted source (`body.source.promoted.is_some()`), i.e. the operation sits inside a const-promoted expression such as a borrowed temporary or a `format_args!` operand.; The operation is one covered by the lint: shift (SHL/SHR), add/sub/mul overflow, div/rem by zero, or a bounds operation like out-of-bounds indexing that yields an unconditional-panic diagnostic.; The arithmetic_overflow lint is enabled/denied (deny-by-default, as shown by `#[deny(arithmetic_overflow)]` in the test stderr) and the operation is not instead a hard const-eval error.; The promoted body is actually reached by the lint pipeline; the fix removes the promoted-source early return, so no extra gating beyond that removal is required.
Pitfalls: Removing the promoted guard raises duplicate diagnostics: 'This PR increases the number of duplicate diagnostics emitted (because the same operator might get linted in both the promoted MIR and the main MIR).' Tests normalize with `-Z deduplicate-diagnostics=yes` and note 'duplicate diagnostic emitted due to `-Z deduplicate-diagnostics=no`'.; Optimization level changes which promotions/paths get linted, so a single-revision test is insufficient; the regression test uses `noopt`, `opt`, and `opt_with_overflow_checks`.; The fix changes acceptance: 'programs containing the above mentioned overflowing promoteds that were accepted earlier will now be rejected'; old tests asserting passing behavior (e.g. `promoted_overflow_opt.rs`) had to be removed or amended.; Do not conflate const-item evaluation errors (`error[E0080]: evaluation of constant value failed`) with the codegen-time lint (`this arithmetic operation will overflow` / `this operation will panic at runtime`).; Pointer-width-dependent shift counts need normalization (`shift left by (64|32)_usize` -> `%BITS%`) so tests pass on 32-bit and 64-bit targets.; Do not treat the transformed-vs-source pair as proof that a compiler was built or that the bug was reproduced; the paired harness only encodes the promoted guard's presence/absence.
Test strategy: Add a UI regression test with revisions `noopt` (`-C opt-level=0`), `opt` (`-O`), and `opt_with_overflow_checks` (`-C overflow-checks=on -O`) plus `-Z deduplicate-diagnostics=yes`. Include the exact reproducer `format_args!("{}", 1 << 32)` and shifted-right, add, sub, mul, div-by-zero, rem-by-zero, and `[1, 2, 3][4]` promoted operands. Pair each promoted form with its non-promoted twin (`let _n = 1u8 << 8;` vs `let _n = &(1u8 << 8);`) and assert both emit `arithmetic operation will overflow` (or `this operation will panic at runtime` for div/rem/OOB). Cover each signed/unsigned integer width and `isize`/`usize`, normalize `%BITS%`, and keep a separate const-item suite for E0080. The minimal pair is a promoted-overflowing body (expect 1 diagnostic) versus the historically guarded variant (expect 0).

### ConstPropLint/const-eval must permit immutable static reads but reject reads of mutable global memory
When constants may mention statics, the blanket 'constant accesses static' rejection is too strong for immutable statics but simply deleting it is unsound: it would let a const read mutable global memory or carry a final value pointing into mutable memory, breaking the as-if-inlined invariant and const-pattern/valtree soundness. The correct rule is mutability-based: allow immutable static reads, halt const-eval interpretation on reads from mutable global memory (`ConstAccessesMutGlobal`), abort valtree construction on mutable reads, and have const validation recursively descend into referenced statics and reject `ConstRefToMutable` and `ConstRefToExtern`. The source frames the invariant: 'constants behave as-if their expression was inlined everywhere and executed at runtime' and 'What we really need is that constants do not *read from* statics that can change their value'.
Preconditions: The const references a static, so `const_refs_to_static` is involved; without the feature the reference is a feature-gate error (E0658, not the old E0013).; Evaluation occurs in a const context, not a static initializer: the machine flag reflects `CanAccessMutGlobal::No` (statics may read mutable globals; consts may not).; For pattern/valtree use, the const must convert to a valtree, which requires the value and everything it refers to to be immutable.; Validation of a const final value must recursively inspect referenced statics; static initializers may skip recursion.; The read check must be conditioned on `alloc.mutability == Mutability::Mut` rather than on `static_def_id.is_some()` alone.
Pitfalls: Blanket rejection of all static access is too strong: reading an immutable static in a const is allowed under `const_refs_to_static` (run-pass `const_refs_to_static.rs`).; Allowing all static access is unsound: reads from `static mut` or interior-mutable statics (`SyncUnsafeCell`, `AtomicUsize`) must be rejected because their value can differ at runtime.; Creating a pointer/reference is not reading through it: `const C2: *const i32 = unsafe { std::ptr::addr_of!(S_MUT) };` is allowed, but `const C2_READ: () = unsafe { assert!(*C2 == 0); };` must fail with `constant accesses mutable global memory`.; Validation, not just evaluation, must reject const final values pointing into mutable memory; otherwise const pattern matching can observe mutable data (`constructing invalid value: encountered reference to mutable memory in `const``).; Extern statics cannot be validated at compile time; a const value referencing an `extern` static must be rejected via `ConstRefToExtern` rather than silently accepted.; Do not copy the static-initializer permission to consts: statics may read mutable global memory, consts may not.; Do not confuse the feature-gate diagnostic change with the semantic permission; the gate still must be enabled and mutability checks still apply.; The paired harness demonstrates the unsound alternative concretely: compile-time propagation of a mutable-static read (returning initial value + 1) versus the runtime read of the mutated value; both are defined executions that merely differ in value.
Test strategy: Use focused UI tests pairing programs that differ only in static mutability/read behavior. Positive run-pass: `static S: i32 = 0;`, `const C1: &i32 = &S;`, `assert!(*C1 == 0)`, and `assert!(matches!(&0, C1));` (the comment notes: 'Computing this pattern will read from an immutable static. That's fine.'). Negative const-eval: `static mut S_MUT: i32 = 0;`, take a pointer with `addr_of!`, dereference in another const, and require `constant accesses mutable global memory`. Negative validation/pattern: `const C: &i32 = unsafe { &S_MUT };` must report `encountered reference to mutable memory in `const`` and matching `C` must report `could not evaluate constant pattern`. Add an interior-mutable static (`SyncUnsafeCell`) and an `extern "C" { static S: i8; }` reference for `ConstRefToMutable`/`ConstRefToExtern`. Also verify the feature-gate error without the gate. Keep const tests separate from static-initializer tests.

### ConstPropLint must not fold NullOp::DebugAssertions before monomorphization
The debug-assertion condition for `assert_unsafe_precondition!` must survive into MIR and be resolved after monomorphization, because the value belongs to the monomorphizing caller, not the library that defined the check. The corrected design adds a `debug_assertions()` intrinsic lowered by `LowerIntrinsics` into `Rvalue::NullaryOp(NullOp::DebugAssertions, bool)`; `ConstPropLint` and `GVN` deliberately return `None` for that NullOp, codegen materializes `sess.opts.debug_assertions`, and the interpreter evaluates it to `false`. Resolving the condition too early (expansion-time `cfg!(debug_assertions)` or const-fold before monomorphization) bakes in the defining library's setting and can delete checks the caller requested.
Preconditions: `LowerIntrinsics` only rewrites a `sym::debug_assertions` call when a target block is present, pushing `Rvalue::NullaryOp(NullOp::DebugAssertions, bool)` to the destination and turning the terminator into `Goto { target }`.; The intrinsic is registered as safe with no arguments returning `bool` (normal unsafety list plus `(0, Vec::new(), tcx.types.bool)` type check).; Every MIR producer/consumer handles the new NullOp: typeck, borrowck, validation, const checking, move-path building, pretty-printing, StableMIR, clippy const-fn qualification, and codegen.; `ConstPropLint` and `GVN` return `None` for `NullOp::DebugAssertions` (the source marker is literally `NullOp::DebugAssertions => return None,`); codegen instead emits `sess.opts.debug_assertions`.; The interpreter evaluates `NullOp::DebugAssertions` to `false` implicitly because 'The checks hidden behind this are always better done by the interpreter'.; `PromoteTemps`' `Validator` accepts `NullOp::DebugAssertions` so it does not make a candidate unpromotable.
Pitfalls: Do not fold `NullOp::DebugAssertions` in ConstPropLint or GVN before monomorphization: the folded value would reflect the defining crate's debug-assertion setting, not the caller's.; Do not guard the unsafe-precondition check with expansion-time `cfg!(debug_assertions)`; the guard must survive into MIR and be resolved at codegen/monomorphization.; Do not make the runtime `precondition_check` generic; it is intentionally monomorphic, `#[inline(never)]`, and `#[rustc_nounwind]` to avoid code-size duplication and to enable the nounwind optimization.; In `InstSimplify`, only mark the unwind edge `UnwindAction::Unreachable` for nounwind calls; closure (`Abi::RustCall`) and coroutine (`Abi::Rust`) ABIs must be classified correctly and the call itself must remain.; Because `assume` codegen is skipped for `OptLevel::No` and `OptLevel::Less`, tests expecting an emitted or optimized `assume` must pin optimization/debug-assertion flags.; MIR tests are sensitive to debug assertions and panic strategy: the new checks add `cfg!(debug_assertions)` branches and `precondition_check` calls, so tests may need `-Cdebug-assertions=no` or `EMIT_MIR_FOR_EACH_PANIC_STRATEGY`.; Treat the paired demonstration as a model of the historical early-fold error, not as proof that the modern compiler is wrong or that a build was reproduced.
Test strategy: Use mir-opt `EMIT_MIR` diffs on `default_boxed_slice`: expected `DataflowConstProp`/`GVN` output keeps `_8 = cfg!(debug_assertions); switchInt(move _8) -> ...` plus a `precondition_check` call rather than a constant. For `Inline`, compile `unwrap_unchecked` with `-Zmir-opt-level=2 -Zinline-mir -Cdebug-assertions=no` so the new `#[inline(never)]` check does not suppress the tested inlining. Add UI `run-fail` tests with `-Copt-level=3 -Cdebug-assertions=yes` matching `unsafe precondition(s) violated: slice::from_raw_parts` and `unsafe precondition(s) violated: hint::assert_unchecked`. For assembly/codegen tests use optimized builds with `-Cdebug-assertions=no` (e.g. `-Copt-level=2 -Cdebug-assertions=no`, `-Copt-level=s -Cdebug-assertions=no`). The minimal pair: caller debug assertions = true and precondition violated -> detected (1); historically early-folded defining-library setting = false -> check deleted (0).
